# 公開デモの保存領域と運用ログ

2026-10-12。実装済みの設計説明。公開先の永続ディスク設定・再デプロイ後の継続確認は別途必要で、文書や環境変数だけでは永続性を証明しない。

## 保存するものと更新するもの

`TAGURI_STATE_DIR` を絶対パスで設定すると、訪問者ごとの観劇記録・評価・感想・興味・お気に入り等を持つ `review/ratings.db`、認証を持つ `auth/auth.db`、復旧コードから本人を識別する鍵 `auth/auth_pepper.txt` をそのディレクトリに保存する。SQLite の補助ファイルも同じディレクトリに作られる。アプリ・推薦計算・記録の取り込み・説明生成は共通の保存先を参照する。

S3 から取得する共通公演カタログは従来どおり `data/` に置く。起動時には一時ディレクトリでアーカイブを検証し、候補ファイルの存在を確認してから交換する。絶対パス、親ディレクトリへの移動、リンク、特殊ファイルは拒否する。アーカイブ中の認証ディレクトリ・DB・pepper は取り込まない。古いカタログにだけあるファイルは交換によって消える。

未設定時は従来のDB・pepper保存先を維持する。カタログ交換時には `data/auth`、`data/review/ratings.db` と補助ファイル、ローカルのお気に入りファイルを保持する。ただし、ホスト側が一時領域を消した場合には残らない。設定画面に一時保存の警告を表示し、JSON APIにも保存モードを含める。

## 公開先の設定

1. Render では **有料サービスの persistent disk** を用意する。無料サービスの任意フォルダを指定するだけでは再デプロイ後の保存を保証できない。
2. 例えばディスクを `/var/data` にマウントし、`TAGURI_STATE_DIR=/var/data/taguri` を設定する。カタログの `data/` と重なるパスは拒否する。ディスクのマウント点そのものではなく子ディレクトリを指定する。
3. 既存データを移す場合は旧プロセスを停止し、旧DBとpepperを同じ環境に保持したうえで `TAGURI_MIGRATE_LEGACY_STATE=1` を設定して起動する。旧pepperを失った認証DBから復旧コードの識別を再現することはできない。
4. 設定後、新しい記録と復旧コードを用意し、プロセス再起動と再デプロイの両方を実施する。同じCookie・復旧コードで同じ記録と推薦が読めることを確認する。公演カタログ交換でも同じ記録が残ることを別に確認する。
5. DBとpepperを同じ時点の安全なバックアップにまとめ、復元試験を行う。バックアップ・定期保持・暗号化・複数インスタンスへの同期は今回の実装には含まない。

公式参考: [Render Persistent Disks](https://render.com/docs/disks)、[Render Free Services](https://render.com/docs/free)。SQLiteを共有せず複数インスタンスで運用する設計ではない。利用者の連続した実履歴を保存する本番では、ホストのディスク障害・バックアップも含めて運用条件を決める。

## 既存データの移行と失敗時

`prepare_storage()` はサーバーの待ち受け・カタログ更新より前に実行する。明示的な移行フラグがない既存データの移行は拒否する。移行先に既にデータがある場合はそれを上書きせず、不足した認証鍵や未移行のDBは起動失敗として扱う。空の既存ディレクトリへの移行も行えるが、マウント点自体を置き換える移行は拒否する。

SQLiteのbackup APIを使い、WAL中の確定済み変更も含めたコピーを一時ディレクトリに作る。pepperもコピーし、まとまった保存領域として公開する。元のDBとpepperは削除しない。旧サーバーが書き込みを続けたままの移行はサポートしない。起動前に停止する。

pepper不足・不正、書き込み不能、移行失敗では、黙って新しい利用者や別の鍵を作らず起動を止める。カタログの取得・展開に失敗した場合も既存のカタログ・DBを保持して起動を止める。実行中のSQLite/ファイル保存エラーは保存成功として返さず、503と再確認の案内を返す。保存後に接続だけ切れた場合は再読み込みして保存結果を確認する。

## 運用ログ

標準出力に1行1JSONの運用イベントを記録する。項目はUTC時刻、固定イベント名、結果、列挙した操作分類、必要な場合のHTTPステータスだけ。イベントは保存領域の準備、カタログ更新、サーバー起動・終了、API書き込み結果、要求処理失敗、デモ初期データ失敗。評価・感想・興味・お気に入り・券・回ごとのメモを分類し、それ以外は `other` とする。

**感想原文、評価内容、公演名、利用者ID、IP、復旧コード、連携コード、Cookie、HTTPヘッダ、生URL・クエリ、例外文・tracebackは運用ログへ出さない。** 公開デモの要求処理失敗には固定メッセージを返す。従来のHTTPアクセスログは引き続き無効。ログ出力先が閉じた場合にも、確定済みの保存を失敗へ変えない。

ログは推薦精度を評価する学習データではない。露出・候補集合・入力の実データ/架空データ区分・推薦方式を記録する実験用ログは、別段階で利用目的・保持期間を決めて実装する。ホスト側の独自アクセスログはこのコードの制御範囲外であり、運用設定で確認する。

`GET /api/health` は認証なしで、固定バージョン `state-storage-v1`、稼働状態、保存モード `temporary` / `configured` を返す。利用者を登録せず、Cookieや復旧コード、パスを返さない。`configured` は設定が存在することだけを示し、永続ディスクの存在や再デプロイ試験の合格を示さない。

## 独立テスト・レビューで確認する条件

- 本人の記録・認証・pepperが同じ保存領域へ入り、再起動後も同じ復旧コードで解決する。
- 評価変更、削除、未評価への戻しが本人の推薦に反映し、他の利用者へ混ざらない。
- 旧データ移行の再実行で既存保存領域を上書きしない。空ディレクトリ、WAL、不正・欠落pepper、書き込み失敗でも元データを失わない。
- カタログ交換で旧DBとpepperを保持し、アーカイブ内のDB・リンク・traversalを受け入れない。途中失敗では交換前の領域へ戻る。
- 永続未設定時の警告・APIモードが正確で、正常・拒否・失敗のログに機密の試験値を含めない。
- 公開先の再起動・再デプロイ後継続確認はローカル試験と分けて報告する。
