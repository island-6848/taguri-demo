# 公開デモの保存領域と運用ログ

2026-10-13（日本時間）更新。実装済みの設計説明。公開先の永続ディスク設定・再デプロイ後の継続確認は別途必要で、文書や環境変数だけでは永続性を証明しない。

## 保存するものと更新するもの

`TAGURI_STATE_DIR` を絶対パスで設定すると、訪問者ごとの観劇記録・評価・感想・興味・お気に入り等を持つ `review/ratings.db`、認証を持つ `auth/auth.db`、復旧コードから本人を識別する鍵 `auth/auth_pepper.txt` をそのディレクトリに保存する。SQLite の補助ファイルも同じディレクトリに作られる。アプリ・推薦計算・記録の取り込み・説明生成は共通の保存先を参照する。

S3 から取得する共通公演カタログは従来どおり `data/` に置く。起動時には一時ディレクトリでアーカイブを検証し、候補ファイルの存在を確認してから交換する。絶対パス、親ディレクトリへの移動、リンク、特殊ファイルは拒否する。アーカイブ中の認証ディレクトリ・DB・pepper は取り込まない。古いカタログにだけあるファイルは交換によって消える。

未設定時は従来のDB・pepper保存先を維持する。カタログ交換時には `data/auth`、`data/review/ratings.db` と補助ファイル、ローカルのお気に入りファイルを保持する。ただし、ホスト側が一時領域を消した場合には残らない。設定画面に一時保存の警告を表示し、JSON APIにも保存モードを含める。

## 公開先の設定

1. （古い案。有料のものは使わない〔dec-free-tier-only〕。デモは記録が消えてよい前提に変わった）Render では **有料サービスの persistent disk** を用意する。無料サービスの任意フォルダを指定するだけでは再デプロイ後の保存を保証できない。
2. 例えばディスクを `/var/data` にマウントし、`TAGURI_STATE_DIR=/var/data/taguri` を設定する。カタログの `data/` と重なるパスは拒否する。ディスクのマウント点そのものではなく子ディレクトリを指定する。
3. 既存データを移す場合は旧プロセスを停止し、旧DBとpepperを同じ環境に保持したうえで `TAGURI_MIGRATE_LEGACY_STATE=1` を設定して起動する。旧pepperを失った認証DBから復旧コードの識別を再現することはできない。
4. 設定後、新しい記録と復旧コードを用意し、プロセス再起動と再デプロイの両方を実施する。同じCookie・復旧コードで同じ記録と推薦が読めることを確認する。公演カタログ交換でも同じ記録が残ることを別に確認する。
5. 下記のオフラインCLIでDBとpepperをまとめてバックアップし、空の別ディレクトリへ復元して同じCookie・復旧コード・記録を確認する。定期保持・暗号化・別ホストへの転送・複数インスタンスへの同期は今回の実装には含まない。

公式参考: [Render Persistent Disks](https://render.com/docs/disks)、[Render Free Services](https://render.com/docs/free)。SQLiteを共有せず複数インスタンスで運用する設計ではない。利用者の連続した実履歴を保存する本番では、ホストのディスク障害・バックアップも含めて運用条件を決める。

### Renderへ設定するときの順序

- 公開中のプロセスがまだ一時保存の場合、**有料化・ディスク追加・再デプロイの前に**既存のDB2種とpepperを安全な別領域へ退避する。ディスクの追加自体が再デプロイを伴うため、ディスク追加後に旧データを取得する順序では失われる場合がある。再デプロイ後に一時領域が消えてから移行フラグを設定しても、失われた記録は戻らない。
- サービスの persistent disk を `/var/data` にマウントし、Environment に `TAGURI_STATE_DIR=/var/data/taguri` を設定する。Build Commandからはディスクにアクセスできないため、初期化・移行は実行プロセスの起動時に行う。
- 旧データを同じ実行環境に安全に保持できるときだけ、停止後に `TAGURI_MIGRATE_LEGACY_STATE=1` を設定して移行する。停止中のオフラインCLIで作ったバックアップを使う場合は、空の `/var/data/taguri` へ復元した後、その保存先で起動する。別の内容を持つ旧保存先と新保存先を混ぜない。
- 初回の保存・復旧確認後、移行フラグを外す。`GET /api/health` の `storage.mode=configured` を確認するが、これだけで合格とはしない。下記の再起動・再デプロイ確認を実施する。
- 課金・ディスク作成はホストの運用変更であり、設定の承認と実行結果を別に記録する。この文書はディスク作成済みを示さない。

## 停止中のオフラインバックアップと復元

`tools/taguri/state_backup.py` はネットワークを使わない運用CLI。**バックアップも復元も、サーバーと全バッチ・書き込み処理を停止してから実行する。** `--server-stopped` は担当者の停止確認を示すフラグで、他プロセスや別ホストの停止を自動検知するものではない。SQLite backupは各DBの確定済みWALを含めてコピーできるが、動作中の3つのDBを同時点の整合した組として保証する機能ではない。

保存領域を準備した環境で、例えば次の順に実行する。出力先の親ディレクトリは事前に用意し、同名のバックアップを再利用しない。

```sh
install -d -m 700 /var/data/taguri-backups

TAGURI_STATE_DIR=/var/data/taguri python tools/taguri/state_backup.py backup \
  --output /var/data/taguri-backups/before-deploy-20261012 \
  --server-stopped

python tools/taguri/state_backup.py restore \
  --backup /var/data/taguri-backups/before-deploy-20261012 \
  --target /var/data/taguri-restored \
  --server-stopped
```

`backup` は現在の保存先から `auth/auth.db`、`auth/auth_pepper.txt`、`review/ratings.db`、`recommendation_exposure.db` を一組のディレクトリへコピーする。`TAGURI_STATE_DIR` 未設定なら旧保存先を読むので、旧pepperもアクセス可能な停止中の環境で使う。DBはSQLite backup APIで作り、integrity・foreign-key検査と必須の利用者スコープ付きテーブルを確認する。バックアップDBはWALに依存しない形式にし、manifestに形式バージョン、作成時刻、4ファイルのサイズとSHA-256を保存する。本文・復旧コード・キー・セッション・元パスは標準出力に出さない。成功/失敗の固定JSONと終了コード0/1だけを返す。

新版manifestは `taguri-state-backup-v2`。露出DBの実際の保存先は `TAGURI_EXPOSURE_DB`、未設定時は `TAGURI_STATE_DIR/recommendation_exposure.db`（保存先自体も未設定ならリポジトリの `state/recommendation_exposure.db`）で、サーバーとCLIは同じパス関数を使う。露出DBが無い・壊れている場合は完全なv2バックアップを作れたことにせず失敗する。復元した露出DBは復元先直下に置く。復元後は `TAGURI_EXPOSURE_DB` の旧領域への指定を外すか、復元先直下へ変更し、同じ保存先を使う。

旧 `taguri-state-backup-v1` の復元は既定で拒否する。露出履歴が含まれないことを了承して認証・記録だけ戻す場合に限り、restoreへ `--allow-legacy-without-exposure` を付ける。露出DBを復元したとは扱わず、起動後に新しい露出履歴から記録する。旧v1から過去の露出を再構成する機能はない。

バックアップ先は**未存在の絶対パス**のみ、復元先は**未存在または空の絶対パス**のみ。既存の記録を持つ保存先、リンク、カタログ内、バックアップ自身と重なる場所への復元を拒否する。マウント点そのものを復元先にせず、その子ディレクトリを使う。既存データを自動削除する・上書きする・強制復元するオプションはない。

一時ディレクトリで全ファイルを用意・検査し、ディレクトリ700、ファイル600にしてfsync後にrenameで公開する。途中失敗では未公開の一時ディレクトリを取り除き、元のDB・pepper・バックアップを削除しない。公開後のディスク同期自体が失敗した場合は、コマンドが失敗を返しても宛先に一組が残る場合がある。宛先を確認し、非空ディレクトリを消して再試行しない。

復元はmanifestのサイズ・ハッシュ、想定したファイル一覧、DB integrity、schema、32バイトのpepper形式を検査する。欠落・破損・不正キーや予期しない追加ファイルを拒否し、復元するコピーも再検査する。ハッシュは偶発的な破損検出で、第三者による改ざんの認証や暗号化ではない。また、形式が正しいpepperがその利用者DBに対応するかは元の復旧コードなしでは確認できない。**復元後に実際の復旧コードで同じ利用者・記録に戻れることを確認する。**

復元試験では `TAGURI_STATE_DIR=/var/data/taguri-restored` で停止していたサービスを起動し、確認後に元の保存先へ戻すか、検証済み復元先を正式な保存先として設定する。元領域を残したまま行い、元と復元先を同時に書き込むサービスを起動しない。バックアップには感想、セッションと認証鍵が含まれるため、公開GitHub・公開S3・共有ログに置かない。同じディスク内のバックアップだけではディスク障害に対応できず、安全な別領域への転送・暗号化・保持期間は別に設定する。

### 公開環境の合格条件

1. 保存先設定後、検証用訪問者AとBを用意する。Aの評価・感想・お気に入りを保存し、Bの記録が変わらないことを確認する。復旧コードとCookieは私的に保管し、公開の検証結果に書かない。
2. サービスの通常再起動後、Aの同じCookieで同じ記録を読めること、別ブラウザで同じ復旧コードによって同じ記録へ戻れることを確認する。
3. GitHub由来の再デプロイ後に同じ確認を行う。カタログ交換後も記録・認証が残ることを確認する。healthのモードだけで代用しない。
4. 全書き込みを停止し、CLIバックアップを空の別領域へ復元する。Aの復旧コード・セッションが同じ利用者を解決し、評価・感想・お気に入りと推薦を読めること、Bの記録が分離されていることを確認する。
5. 非空の復元先・欠落DB・破損DB・不正pepperでは失敗し、元データに変化がないことを独立テストで確認する。検証日時・サービス版・操作種別と合否だけを記録し、秘密・原文感想を含めない。

ローカル試験の成功と、Render上でこの5条件を実施した結果は分けて報告する。公開先の接続や操作権限がない場合は公開環境の試験を未実施として扱い、永続保存の保証を表示しない。

## 既存データの移行と失敗時

`prepare_storage()` はサーバーの待ち受け・カタログ更新より前に実行する。明示的な移行フラグがない既存データの移行は拒否する。移行先に既にデータがある場合はそれを上書きせず、不足した認証鍵や未移行のDBは起動失敗として扱う。空の既存ディレクトリへの移行も行えるが、マウント点自体を置き換える移行は拒否する。

SQLiteのbackup APIを使い、WAL中の確定済み変更も含めたコピーを一時ディレクトリに作る。pepperもコピーし、まとまった保存領域として公開する。元のDBとpepperは削除しない。旧サーバーが書き込みを続けたままの移行はサポートしない。起動前に停止する。

pepper不足・不正、書き込み不能、移行失敗では、黙って新しい利用者や別の鍵を作らず起動を止める。カタログの取得・展開に失敗した場合も既存のカタログ・DBを保持して起動を止める。通常の保存API処理内で起きたSQLite/ファイル保存エラーは保存成功として返さず、503と再確認の案内を返す。認証登録・復旧の処理中など、この保存APIの例外処理の外で起きた障害は、固定の `request_failed` イベントを記録して接続を切断する場合がある。保存後に接続だけ切れた場合は再読み込みして保存結果を確認する。

## 運用ログ

標準出力に1行1JSONの運用イベントを記録する。項目はUTC時刻、固定イベント名、結果、列挙した操作分類、必要な場合のHTTPステータスだけ。イベントは保存領域の準備、カタログ更新、サーバー起動・終了、API書き込み結果、要求処理失敗、デモ初期データ失敗。評価・感想・興味・お気に入り・券・回ごとのメモを分類し、それ以外は `other` とする。

**感想原文、評価内容、公演名、利用者ID、IP、復旧コード、連携コード、Cookie、HTTPヘッダ、生URL・クエリ、例外文・tracebackは運用ログへ出さない。** 公開デモの要求処理失敗には固定メッセージを返す。従来のHTTPアクセスログは引き続き無効。ログ出力先が閉じた場合にも、確定済みの保存を失敗へ変えない。

ここで説明する運用ログは推薦精度を評価する学習データではない。推薦の露出・候補集合・入力の実データ/架空データ区分・推薦方式を記録する機能は、運用ログとは別に導入済み。詳細と検証条件は[推薦露出ログ](recommendation-exposure.md)を参照する。今回の新版バックアップは認証DB・記録DB・別DBの推薦露出をコピーする。記録DB内の感想嗜好も保持する。旧v1は露出DBを含まないため、露出を復元済みとは扱わない。ホスト側の独自アクセスログはこのコードの制御範囲外であり、運用設定で確認する。

`GET /api/health` は認証なしで、固定バージョン `state-storage-v1`、稼働状態、保存モード `temporary` / `configured` を返す。利用者を登録せず、Cookieや復旧コード、パスを返さない。`configured` は設定が存在することだけを示し、永続ディスクの存在や再デプロイ試験の合格を示さない。

## 独立テスト・レビューで確認する条件

- 本人の記録・認証・pepperが同じ保存領域へ入り、再起動後も同じ復旧コードで解決する。
- 評価変更、削除、未評価への戻しが本人の推薦に反映し、他の利用者へ混ざらない。
- 旧データ移行の再実行で既存保存領域を上書きしない。空ディレクトリ、WAL、不正・欠落pepper、書き込み失敗でも元データを失わない。
- カタログ交換で旧DBとpepperを保持し、アーカイブ内のDB・リンク・traversalを受け入れない。途中失敗では交換前の領域へ戻る。
- 永続未設定時の警告・APIモードが正確で、正常・拒否・失敗のログに機密の試験値を含めない。
- 公開先の再起動・再デプロイ後継続確認はローカル試験と分けて報告する。

## 公開版の本人用書き出し

公開版の `GET /export.json` は有効なセッションがある本人の記録だけを返す。URLや本文で利用者IDを指定しても書き出す人は変わらない。各対象テーブルに `user_id` 列があることを確認し、ない旧テーブル・共有テーブルは除外する。お気に入りは本人のDB設定だけを含め、共有の `declared.json` は含めない。設定画面に示す件数も本人の書き出しと同じ範囲を使う。

公開版の `/data.zip` は共通DB・取得物を丸ごと持ち出すため拒否し、設定画面にもリンクを出さない。ローカル1人用の書き出しとコピー機能は従来の用途で利用できる。本人向けJSONはDB復旧用バックアップではなく、認証DB・pepper・他人の記録を含めない。

## サービス起動時の保存ゲート

`deploy/render-service.yaml` は公式Render JSON schemaで独立検証した構成案で、ホストには未適用。schema検証の記録はサービス検証記録を参照する。初期状態は `maintenanceMode.enabled=true` として一般アクセスを止める。管理者による起動・保存検証と、問い合わせ・削除・公演情報の権利など公開条件の合格後に、明示的にメンテナンスを解除する。構成ファイルの適用だけをサービス一般公開の完了とは扱わない。

Renderでサービス版を起動する場合、`TAGURI_STATE_DIR=/var/data/taguri` と `TAGURI_STATE_MOUNT=/var/data` を指定する。指定したマウントが実在し、保存先がその配下にあることを起動前に確認する。露出DBも同じ保存先内に置く。任意の一時フォルダにパスを設定しただけでは起動しない。マウント確認は再起動・再デプロイ後の継続保存試験やホスト障害の保証の代わりにはならない。

Render以外でのローカル検証は `TAGURI_ALLOW_LOCAL_SERVICE=1` を明示し、テスト用保存領域を指定する。この構成は公開サービスの永続性を確認したものとして扱わない。新サービスはデモとは別の空保存領域から始め、デモの架空評価を移行しない。
