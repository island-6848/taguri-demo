# 「たぐり」基本設計書（全体概要）

**目的: 演劇を観る人が、興味のありそうな公演を見逃さず、探す手間をかけずに次に観る公演を決められるようにする。**

- 位置づけ: **実装を細部から離れて一望するための文書。** 基本設計書の標準的な 7 項目（機能一覧・業務フロー図／システム構成図・画面設計図・帳票設計図・バッチ設計図・データベース設計図・外部インターフェース設計図）に沿って構成するが、**中身は「システム全体をざっくり把握する」粒度に留める。** 画面ごとの操作・DB のカラム定義・意匠の規約など、作るときに必要な粒度の詳細は [000007-taguri-design.md](000007-taguri-design.md) に集めてあり、この文書には書かない。個別仕様書（「たどる」「相関図」）はさらにその下にある。セキュリティの点検は [000007-taguri-security-review.md](000007-taguri-security-review.md) に分けてある。
- 起案の元: [#000002 知識処理システム企画書](000002-system-proposal-taguri.md)
- この文書の主張のうち、画面の構成・意匠の規約に関わる部分は `tools/taguri/test_design.py` で機械的に検査している。書いたことと実装が食い違えば、その検査が落ちる
- 執筆: 2026-08-27

---

## これは何か

**演劇を観る人が、次に何を観るか決めるための道具である。** 自分が観た公演に付けた ◎○△× だけを材料にして、まだ初日を迎えていない公演の中から「これは合いそうだ」というものを毎週 10〜15 件、理由付きで出す。それ以外の画面はすべて、この 1 つの答えを支えるための脇道である。

**自分専用の道具である。** 記録は自分の端末の中だけに置き、他人と共有しない。演劇を観る人なら誰でも同じ仕組みで使えるが、いま実際に使っているのは起案者本人だけである。

## 1. 機能一覧

機能を「利用者が押して使うもの」と「裏で自動に動くもの」に分け、**画面数や操作の列挙はしない**（それは詳細設計書の役目）。

| 分類 | 何をするか |
|---|---|
| **推薦** | 観劇履歴の統計から順位を付けた週次推薦を出し、初日が近い未回答・興味あり・お気に入りを開幕リマインドで知らせる |
| **好みの学習**（自動） | 観劇履歴とクレジットから作り手の名簿を、あらすじと評価の相関から内容傾向を作る |
| **申告の管理** | 履歴に出てこない「見逃したくない名前」をお気に入りとして登録・解除する |
| **反応の収集** | 推薦への三択（興味あり／なし／持っている）、観た公演の評価（◎○△×）・感想、観ればよかったの申告を受ける |
| **観劇予定の管理** | 観る回をカレンダー・チケットに登録し、確定・取り消しをする |
| **記録の管理** | 公演の登録・修正・統合・取り消し／復元を行う |
| **記録の可視化**（読むだけ） | 眺める・たどる・観劇史年表・日記帳で、記録と学習結果を振り返る |
| **検索・設定** | 過去の記録・候補を検索し、都道府県の既定・書き出しなどの決めごとを扱う |

**答えを出すのは「推薦」だけである。** ほかはすべて、推薦の材料を見せているか、推薦への反応を受け取っているかのどちらかであり、この線引きが機能の設計原則になっている。

## 2. 業務フロー図

利用者から見た業務（＝観劇の意思決定）は、次の輪として回る。

```
                材料を集める（自動）
              あらすじ・クレジット・お気に入りの新着
                      │
                      ▼
                知識を作る（自動）
          作り手の名簿・内容の傾向・網の重み
                      │
                      ▼
              一覧を出す（利用者が開く）
            週 10〜15 件、理由と出典つき
                      │
                      ▼
             反応を戻す（利用者が押す）
      興味あり／なし・すでに持っている・◎○△×
                      │
                      └──── 次に開いたときの計算に使われる
```

**輪を回すのは、利用者がショートカットを 1 つ押すことだけである。** 定期実行するプロセスは無い。押すたびに、材料を集める→知識を作る→一覧を出す、が順に走り、ブラウザが開く。開いた画面で押した反応は、その場で記録に書き戻り、次に押したときの計算に使われる。**「見て終わり」ではなく、押すたびに賢くなっていく仕組みである点が、この輪の核である。**

**外部とのやり取りで転ぶ段では止めない。** 相手のサーバや API の枠といった自分では制御できない事情で失敗しうる段（メールの取り込み・候補の取得・カレンダーの取り込みなど）は、失敗しても一覧を出す方を優先する。**止めるのは推薦の計算そのものが失敗したときだけ**で、そのときは出すものが無いので、そこで打ち切る。

## 3. システム構成図

```
┌───────────────────────┐     ┌────────────────────────────┐
│  外部のデータ源         │      │  Gemini API                │
│  ・ステイジーズカレンダー │ ──▶ │  （あらすじ抽出・メール判定・  │
│  ・CoRich 舞台芸術!      │      │  　人名判定・感想語抽出）      │
│  ・ステージナタリー/SPICE │      └──────────────┬─────────────┘
│  ・劇場公式サイト        │                     │
│  ・購入確認メール(Gmail) │                     ▼
└──────────┬───────────┘      ┌────────────────────────────┐
           │取得（1 req/秒以下）  │  ローカルの一時プロセス        │
           └───────────────▶ │  （127.0.0.1・起動ごとに鍵を発行）│
                              │  ・材料を集める／知識を作る       │
                              │  ・推薦を計算する                │
                              │  ・反応を受けて書き戻す           │
                              └──────────────┬─────────────┘
                                             │読み書き
                                             ▼
                              ┌────────────────────────────┐
                              │  端末内のデータ                │
                              │  ・SQLite（状態：評価・反応・券） │
                              │  ・ファイル（取得物：候補・あらすじ）│
                              └────────────────────────────┘
                                             ▲
                                             │画面の表示・反応の送信
                              ┌────────────────────────────┐
                              │  ブラウザ（同じ端末内）          │
                              └────────────────────────────┘
```

**サーバは公開しない。** 待ち受けは `127.0.0.1` に固定し、外部からは一切アクセスできない。ブラウザから外部へ直接データを取りに行くこともしない ── 外部とのやり取りは、すべてローカルの一時プロセス側に集約している（詳しくは [000007-taguri-security-review.md](000007-taguri-security-review.md)）。

## 4. 画面設計図

**入口は 1 つで、左のナビゲーションで画面を移動する 1 つのシステムである。** 画面ごとに別々のファイルを開かせる形はとっていない。個々の画面の入出力項目は詳細設計書（[000007-taguri-design.md](000007-taguri-design.md)）に譲り、ここでは画面の群構成だけを示す。

```
たぐり
├─ おすすめ（答えを出すのはここだけ）
│  ├─ 今週のおすすめ
│  ├─ 開幕リマインド
│  ├─ 興味あり
│  └─ お気に入り
├─ 公演カレンダー
├─ 購入済み公演
├─ 観た公演の評価
│  ├─ 評価一覧
│  ├─ 未評価
│  └─ 感想
├─ 公演情報の登録（入力専用）
├─ 記録を見返す（読むだけ）
│  ├─ 眺める
│  ├─ たどる
│  ├─ 観劇史年表
│  └─ 日記帳
├─ 探す
└─ 設定
```

**答えを出すのは「おすすめ」群だけ**という線を、画面設計の基準にしている。それ以外はすべて、答えを作るための材料を見せているか、答えへの反応を受け取っているかのどちらかである。

## 5. 帳票設計図

**この系には、伝票・請求書のような対外的な帳票は存在しない。** 1 人用のローカル道具であり、印刷や他システムへの提出を前提にした固定様式の出力は無い。最も近いのは次の 2 種である。

| 出力物 | 位置づけ | 形式 |
|---|---|---|
| **週次推薦一覧** | この系が出す唯一の「答え」。理由・出典つきで 10〜15 件を並べる | 画面表示（HTML）。紙・PDF には出さない |
| **書き出し（export.json）** | 記録・評価・感想・お気に入りを、他の道具でも読める形で保存する | JSON（1 ファイル） |
| **別端末への持ち出し（data.zip）** | 記録・取得物・ポスターを丸ごと固めたもの。LAN 越しの同期はしない | ZIP（1 ファイル） |

## 6. バッチ設計図

**利用者がショートカットを押すたびに、次の順で処理が走る。** 定期実行（cron 等）は無く、起動の契機は常に利用者の操作である。

```
① 購入確認メールの差分を取り込む（--mail 指定時のみ・毎回）
② 評価待ちの公演を洗い出す（毎回）
③ 新しい候補を取得し、あらすじを抽出する（--fetch 指定時のみ・月 1 回・約 5 分）
④ お気に入り登録名で直接検索する（毎回）
⑤ カレンダーを取り込む（毎回）
⑥ 推薦を計算し、出した一覧を保存する（毎回）
⑦ 差分のポスターを取り込む（毎回）
⑧ 記録を見返す画面の材料を組み立てる（毎回）
⑨ サーバを起動し、ブラウザで開く（毎回）
```

**外部とのやり取りで失敗する段（①③④⑤⑦）では処理を止めない。** そこで止めると一覧そのものが開かず、その週は何も見られなくなるためである。取れなかったことは画面に出すが、開くことを優先する。**止めるのは⑥だけ**で、推薦の計算が失敗したら出すものが無いのでそこで打ち切る。

**③（新しい候補の取得）だけが重い処理である。** 母集団は月 1 回更新されるカレンダーに合わせて月 1 回だけ取りに行き、それ以外の週は数秒で一覧が開く。取得は 1 リクエスト/秒以下を守る（詳しくは [000007-taguri-security-review.md](000007-taguri-security-review.md)）。

## 7. データベース設計図

**書き戻しが要る「状態」は SQLite 1 本にまとめ、外部から取ってくる「取得物」は取り直しがきくファイルのまま置く。** 状態が複数箇所に分かれると、画面からの書き込みと次回の読み出しが別の経路を通ることになり、反映漏れが起きる（過去に実際に起きている）。テーブル単位の役割は、次の 4 つの塊として見ると分かりやすい。カラム定義は詳細設計書に譲る。

```
状態（data/review/ratings.db。画面から書き戻すのはここだけ）

┌─ 観た公演の記録（中心は works）───────────────────────┐
│ works ← attendance・splits・excluded・fixes・         │
│         merges・hand_credits・visit_note              │
└──────────────────────────────────────────────────────┘

┌─ 推薦とのやり取り ─────────────────────────────────────┐
│ presented・viewed・reaction・ticket                    │
└───────────────────────┬──────────────────────────────┘
                         │ 参照する
                         ▼
┌─ 取得物（data/review・data/tickets・data/credits。ファイルのまま置く）─┐
│ 候補・あらすじ／クレジット・お気に入りの新着・カレンダー・              │
│ 観た公演の履歴（これだけは取り直せない ── メールという一次情報の写し） │
└────────────────────────────────────────────────────┘

┌─ 単独（他のどれとも結び付かない）───────────────────────┐
│ missed（観ればよかった）・rank_weight（推薦の重み）・     │
│ app_setting（都道府県の既定などの設定）                   │
└──────────────────────────────────────────────────────┘
```

**works が状態の中心である。** ◎○△×・感想・観劇回数を持ち、同じ公演の記録の直し（`fixes`）・分割（`splits`）・除外（`excluded`）・統合（`merges`）・手入力の補い（`hand_credits`）は、すべて works の記録を正しく保つための周辺である。**候補・あらすじなどの「取得物」は消えても取り直せるが、観た公演の履歴（購入確認メールの写し）だけは取り直せない**（メールという一次情報がその時点でしか読めないため）。

## 8. 外部インターフェース設計図

| 相手システム | 方向 | 形式・手段 | 何を渡す／受け取るか | 頻度・制限 |
|---|---|---|---|---|
| **ステイジーズカレンダー** | 受信 | 公開 Google スプレッドシートの CSV 一括ダウンロード | 公演の母集団（団体・劇場・期間） | 月 1 回 |
| **CoRich 舞台芸術!** | 受信 | 検索・取得 | 母集団の補完、過去公演の一覧 | 候補取得時のみ・1 req/秒以下 |
| **ステージナタリー Atom／SPICE RSS** | 受信 | 公開フィード | 新報の公演情報 | 毎回（差分） |
| **劇場公式サイトのフィード** | 受信 | RSS／Atom（配信がある館のみ） | 劇場が自ら出す公演情報 | 毎回（差分） |
| **各公演の公式サイト** | 受信 | ページ取得 | あらすじ・クレジット | 候補取得時のみ・1 req/秒以下 |
| **購入確認メール（Gmail）** | 受信 | Gmail API（`gmail.readonly` スコープの OAuth）。同意は画面の「取り込み」を押すたびに求める | 観た公演の特定に使う件名・本文 | 毎回（差分）。送信・削除は行わない |
| **Gemini API** | 送受信 | 構造化出力（`responseSchema`）の API 呼び出し。`urllib` で直接叩く（専用 SDK は使わない） | メール判定・あらすじ抽出・人名判定・感想語抽出などの断片（好みの本体は渡さない） | 材料を集める段のみ |
| **OpenStreetMap（geocoder）** | 受信 | ジオコーディング API | 劇場名から座標を引く | 初回のみ・引いた結果は端末内に保存し二度と引かない |

**外部への取得は、すべてローカルの一時プロセス側からだけ行う。** 画面（ブラウザ）が外部と直接やり取りすることはない。取得の範囲・頻度・アクセス権限がすべて守られているかは、[000007-taguri-security-review.md](000007-taguri-security-review.md) で個別に確認済みである。

## 完成の線

**一周が閉じることだけを完成とする。** ショートカット 1 つで材料の取り込みから一覧の表示までが走り、開いた画面で押した反応が記録に書き戻り、もう一度実行すると反映された一覧が出る ── ここまでを完了条件とし、写真からの公演特定・記録を見返す画面の作り替え・検索の強化は次に回した。詳しい完了条件は [000007-taguri-design.md](000007-taguri-design.md) の 8 章にある。
