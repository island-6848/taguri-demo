## 目的

**演劇を観る人が、興味のありそうな公演を見逃さず、探す手間をかけずに次に観る公演を決められるようにする。**

この文書に書く内容は、この 1 文のどの部分を実現しているかを言えるものだけにする。言えない内容は書かない。

## 機能一覧（ツリー図）

```
たぐり
├─ 推薦する
│   ├─ 週次推薦：開幕前の公演から、興味のありそうなおすすめを 15 件提示する
│   └─ 開幕リマインド：初日が近い未回答・興味あり・お気に入りの公演を知らせる
├─ 学習する
│   ├─ 作り手の名簿：観た公演のクレジットから、高評価につながりやすい人物を自動で集計する
│   ├─ 内容の傾向：あらすじの要素と評価の関係を自動で集計する
│   └─ お気に入り：履歴に出てこない見逃したくない名前を、本人が直接登録する
├─ 反応を集める
│   ├─ 三択：推薦した公演に「興味あり／興味なし／すでに持っている」で反応する
│   ├─ 評価・感想：観た公演に ◎○△× と感想を付ける
│   └─ 観ればよかった：見逃した公演をあとから申告する
└─ 記録を管理する
    ├─ 観劇予定：観る回をカレンダー・チケットに登録し、確定・取り消しをする
    ├─ 記録の登録・修正・統合・取り消し／復元：観た公演の記録を直す・束ねる・戻す
    ├─ 振り返る：眺める・たどる・観劇史年表・日記帳で記録を見返す
    └─ 探す・設定：名前や題材で過去を検索し、都道府県の既定などを決める
```

**それぞれの機能を実現している技術は、次のとおりである。**

| 機能 | 実現している技術 |
|---|---|
| 推薦する | 観劇履歴から数えた当たり率・信頼度を、固定の計算式で合成して順位を付ける（Python。学習・推論はしない） |
| 学習する | 履歴とクレジットの集計（Python）と、あらすじからの要素抽出（LLM・Gemini API） |
| 反応を集める | ブラウザの操作 → ローカル一時プロセスへの HTTP 通信 → SQLite への書き込み |
| 記録を管理する | SQLite（状態の保存）と、検索・集計のための Python コード |

**「推薦する」が使う当たり率・信頼度は、次のような値である。** 役職と人物の組み合わせ（例:「演出・田中太郎」）ごとに、観た本数 `n` と、そのうち高評価だった本数 `o` を数え、次の 2 つを計算する。

- **当たり率** = (o + 1) ÷ (n + 2)。単純な割合（o ÷ n）ではなく、少し補正してある。補正が無いと、1 回しか観ていない人がたまたま高評価だっただけで「当たり率 100%」になってしまうためである
- **信頼度** = n ÷ (n + 3)。観た本数が多いほど 1 に近づき、少ないほど 0 に近づく。当たり率が高くても、まだ実績が少ない人物の値を割り引くための重みである

例えば「5 回観て 4 回高評価」なら当たり率 ≈ 0.71・信頼度 = 0.625、「1 回観て高評価だっただけ」なら当たり率 ≈ 0.67・信頼度 = 0.25 になる。**当たり率はほぼ同じでも、信頼度が大きく違うため、実績が少ない人物の寄与は自動的に抑えられる。**

**この 2 つの補正（+1/+2、+3 という数）に、実測の裏付けは無い**（[検証 035](verification/035-scoring-constants-audit.md)・2026-08-21）。起案者から「今の採点方法は裏付けのある採点方法か」と問われ、これらの定数を 1 つずつ差し替えて、当たり外れを見分ける力（AUC）が変わるかを測った。信頼度の定数を 1 や 10 にしても、無くしても、当たり率の補正を無くしても強めても、差はすべて標本の取り方によるブレ（±0.118）の範囲に収まり、意味のある差は出なかった。**つまりこの 2 つの補正は、統計でよく使われる標準的な平滑化の形を理屈のある形で採っているだけで、このデータに合わせて調整した値ではない。** 唯一実測の裏付けがあるのは「高評価の基準を ◎ だけに絞る」ことで、これは実際に見分ける力に差が出ている（○ 以上を含めると 0.517、◎ だけなら 0.694）。評価が 200 件程度に増えた時点で、この 12 通りを測り直す予定である。

## 全体の構成

**「材料を集める」から「評価を受ける」までの 4 段が、具体的にどの部品を通って実行されるかを示す。各段で、技術的に何が起きているかも添える。**

```
                    外部の情報源
              （劇場のサイト・チケットの発券情報・購入確認メールなど）
                         │  HTTP でページ・CSV・フィードを取得し、メールは
                         │  IMAP で読む（いずれも 1 リクエスト/秒以下）
                         ▼
                  取得物（ファイル）
             取得した内容を JSON・JSONL としてディスクに保存する。
             次に取得し直すまで、このファイルをそのまま使い回す
                         │
                         ▼
        ローカルの一時プロセス（127.0.0.1。http.server による HTTP サーバ）
             学習する：クレジットと評価の組を数え、役職ごとの当たり率を
             ルールベースで集計する。あらすじの要素抽出だけ、Gemini API を
             urllib で直接呼び、スキーマで指定した形の JSON を受け取る
             推薦する：集計した強さに重みを掛けて合計するスコア計算
             （Σ w × 強さ）で順位を付ける。AI はここには入らない
                         │  組み立てた一覧を HTML として返す
                         ▼
                      ブラウザ
             埋め込まれた素の JavaScript が、押した三択・評価・感想を
             fetch() でトークン付きの POST（例: /api/react）として送る
                         │  POST を受け取り、内容を SQLite に書き込む
                         ▼
                  SQLite（「記録を管理する」が保存する場所。
                  INSERT・UPDATE で反応・評価を書き込む）
                         │
                         └──▶ 次に起動したとき、SELECT で読み出されて
                              「学習する」「推薦する」の材料になる
```

**利用者から見ると、やることは 1 つしかない。** ショートカットを押すと、外部から集めた材料をもとに学習と推薦が動き、ブラウザに一覧が出る。そこで利用者が押した反応は SQLite に残り、次にショートカットを押したときの学習・推薦にそのまま使われる。**この「押した反応が次に活きる」という輪になっていることが、利用者が公演を探す手間を重ねなくても、使うほど自分に合った公演が出てくるようになる理由である。**

## 技術面から見た構成

**上の図に出てきた部品を、技術の言葉で並べ直す。** コードのファイル名・関数名までは書かない（それは [000007-taguri-design.md](000007-taguri-design.md) の役目）。

```
        外部接続：IMAP／Gmail API・Gemini API（あらすじ抽出などの LLM 呼び出し）・
                  公演情報の各種フィード・OpenStreetMap
                              │  取得する
                              ▼
┌────────────────────────────────────────────────────────┐
│ バックエンド（ローカルの一時プロセス。127.0.0.1・http.server） │
│                                                          │
│ 言語：Python（標準ライブラリ中心）                            │
│  ├─ 学習する・推薦する ── 判断と計算はすべてここで行う         │
│  ├─ 保存（状態）：SQLite                                    │
│  └─ 保存（取得物）：ファイル（JSON・JSONL）                    │
└───────────────────┬──────────────────▲───────────────────┘
     HTML を生成して返す│                  │ fetch() がトークン付き
                       ▼                  │ POST として送る
┌────────────────────────────────────────────────────────┐
│ フロントエンド（ブラウザに埋め込まれた素の JavaScript）          │
│ 判断はしない。一覧を表示し、利用者が押した反応を送り返すだけ       │
└────────────────────────────────────────────────────────┘
                       ▲
                       │ 利用者が見て、押す
```

**フロントエンドとバックエンドの境目は、この図のとおりくっきり分かれている。** 推薦の順位・学習の集計といった「判断」は、すべてバックエンド側で計算する。フロントエンド（素の JavaScript。フレームワークは使わない）は、バックエンドの Python が生成した HTML の中に埋め込まれて表示されるだけで、それ自身は何も判断しない。利用者が押した三択・評価・感想は、`fetch()` でバックエンドの API に送り返され、そこで初めて SQLite に書き戻される。

**AI の呼び出し先は、2026-08-27 に claude CLI から Gemini API へ切り替わった。** それまでは、あらすじの要素抽出などを行う全 6 か所が `claude` CLI をサブプロセスとして呼んでいた（`ANTHROPIC_API_KEY` を環境に持たないため）。しかし claude CLI は対話用セッションと同じ枠・同じログイン状態を使っており、専用の課金経路も専用の資格情報も持たなかった。「コスト面でもセキュリティ面でもまずいのでは」という指摘を受け、専用の API キーを使う Gemini API に切り替えた。**公式 SDK（`google-genai`）は pip install が要るため使わず、REST API を `urllib` で直接呼んでいる**（標準ライブラリだけで完結させる方針を保つため）。あわせて、claude CLI 時代は「プロンプトで JSON 形式を指定し、正規表現で切り出す」当て推量をしていたが、**Gemini は構造化出力（JSON Schema を強制する `responseSchema`）に対応しているため、期待する形をスキーマとして渡し、崩れた出力そのものを起こさせない形に変わった。**

**この技術を選んだ理由は、次の 4 点にまとめられる。**

- **公開のサーバを持たず、Python の標準ライブラリだけで完結させる。** 観劇記録は利用者本人の行動履歴であり、外部のサーバやアカウントに預けると、得られる価値の割に負う責任が大きい（企画書 2 章）。
- **反応を集める・記録を管理するが書き戻す「状態」は SQLite 1 本にまとめ、学習するが読む「取得物」はファイルのまま置く。** 状態が複数箇所に分かれると、画面からの書き込みと次回の読み出しが別の経路を通ることになり、反映漏れが起きる（過去に実際に起きた）。
- **画面は静的な HTML ではなく、一時プロセスを立てて動かす。** 静的な HTML では利用者の反応を記録に書き戻せず、「反応を集める → 学習する → 推薦する」の輪が閉じない。
- **AI は、規則で書けない変換にだけ使う。** 推薦するの順位を計算する処理そのものには AI を使わないので、同じ記録からは毎回同じ順位が出る。
