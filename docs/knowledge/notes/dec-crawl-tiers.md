起案者の指示（2026-10-21）「最優先の目標は、GitHub Actions の無料枠内で新規公演情報を毎日安定して更新できるようにすること」。優先順位も起案者が決めた:

1. 新しい公演の発見と登録
2. 直近に開かれる公演の情報・出演者・あらすじの更新
3. 持っている公演の変更の確認
4. 過去の公演の補完
5. 過去の公演のポスター・あらすじ

「下位の処理が大量の実行時間を消費しても、上位の処理が停止しない設計にする」「実測値が得られるまでは制限を緩めない」。

**何が起きていたか**〔f-crawl-step-times-1021〕
- 10-17〜10-20 の決まった時刻の Catalog は、4 回とも計画の段で止まった。直近 31 日の分数（10-13〜10-20 の過去の公演・ポスター・本文で約 1,300 分）と、これからの毎日の更新の見積もりを足すと、上限 1,600 分に届いたため。
- 計画の段は、これからの毎日の更新の分（1 日 15 分）を取っておいていた。それでも止まったのは 2 つの理由から。
  - 時間の上限の無い段（ポスターを R2 に入れる、名前の索引）が、計画の数に入っていなかった。
  - 下位の処理が残りを余白なく使い切っていた。
- 新しい公演を CoRich で見つけるのは週 1 の取り直しだけだった。週 1 は分が足りないと毎日の更新に落ちるので、新しい公演が 1 週間以上載らないおそれがあった。

**決めたこと**
- **計画（free_tier.py plan）**
  - 毎日の更新の見積もりは 15 分のまま（実測は 3〜5 分だが、毎日の発見を足した実測がまだ無いので緩めない）。
  - 下位の処理と手で動かすもの（再生・予行・本文）は、残りから余白 BACKGROUND_MARGIN（30 分）を引いた分だけを使う。
  - 下位の処理は順に配る。過去の公演（読み取り・D1・名前の索引）が先、ポスター（取る・R2 に入れる）があと。
  - ポスターを R2 に入れる段にも上限（upload_minutes、最大 30 分）を付けた。名前の索引は、過去の公演を読んだ日だけ動かす。
  - 試験（test_background_work_never_takes_the_daily_reserve）: 下位の処理が毎日、計画の上限まで使い切っても、40 日続けて毎日の更新が動く。
- **新しい公演の発見を毎日に**（fetch_candidates.py、run.py の --discover）
  - サイトマップ（4 ファイル）を読み、前回の最新 id より新しい公演だけを読む（差分）。前回の結果（候補・クレジット）は使い回す。
  - クレジットが空のこれからの公演と、サイトマップの更新日（lastmod）が前回より新しいこれからの公演を読み直す。これが 3 の変更の確認で、公演ページを読まずに見分けられる。
  - 読む順は 1 → 2 → 3。上限（DISCOVER_MINUTES、5 分）で止めたら、読み終えた id までを控え、続きは次回に読む（飛ばさない）。
  - 読み直しに失敗したら、前回のクレジットを残す（消さない）。更新日も前回のままにして、次回また読む。
- **段の並び**（catalog.yml）
  - 毎日の更新: 取り直し → あらすじの待ち → D1 に入れる → 控え（backup）。控えは、下位の段が止まっても毎日できるよう前に移した。
  - 4（過去の公演）→ 5（ポスター）の順。下位の段はどれも continue-on-error と時間の上限つきで、保存の段まで進む。
  - 手で動かすときの既定は daily にした（週 1 は分を多く使う）。
- **測る**（free_tier.py check）
  - この実行の段ごとの秒数を API から読み、控え（usage.json の runs、新しい 60 回）に残す。毎日の更新の段と下位の段に分けた分数と、毎日の更新の実測の並びを Summary に出す。止めた日は数えない。
  - D1 の読み出しは 2 つを出す。直近 24 時間の Worker と取得の合計（`wrangler d1 info --json` の rows_read_24h）と、この実行の取得の段の rows_read（各段の wrangler の出力を tee で残したログから）。上限は 1 日 300 万行で知らせる（無料 500 万行）。
- **知らせ方**
  - 予算が足りずに毎日の更新を止めた日と、上限の 8 割を越えた日は、失敗にしない。このリポジトリの issue「無料枠の注意（取得）」に書く（開いていればコメントを足す。issues: write）。
  - 数えが読めないとき（Actions の分・Worker の R2 の数え）は失敗にする（本当のエラーは隠さない）。
  - D1 の分析が読めないとき（鍵の権限）は注意だけにする。
  - 古い catalog.yml との行き違いを防ぐため、止めた日を失敗にしないのは TAGURI_PLAN_SOFT_STOP=1 のときだけ。古い yml は、この段の失敗であとの段を止めている。

**見込み**（実測の 3〜5 分と、上限の値から）
- 毎日の更新: 実際は 5〜10 分（発見の上限 5 分を含む）、見積もり 15 分。月の毎日の分は最大 31 × 15 = 465 分で、上限 1,600 分の 3 割。
- 週 1 の取り直し: 見積もり 120 分のまま。サイトマップの差分になってからの実測は無い。
- 新しい公演が載るまで: CoRich のサイトマップは毎日 1 時台に作り直され、取得は 4:17 に動く。サイトマップに載ってから最長で 1 日と少し。1 日に読める新しい公演は、5 分で約 250 件（1.1 秒に 1 枚）。それを越える日の分は次の日に回る。

**分からないこと**
- サイトマップの lastmod が、出演者の追加などの公演の更新で進むか（q-sitemap-lastmod-meaning）。
- 毎日の発見を足したあとの毎日の更新の実測。点検の段が控えるので、2 週間ほどたまってから 15 分の見積もりを見直す。
