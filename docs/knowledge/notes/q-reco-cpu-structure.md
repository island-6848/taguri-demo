#138 の続き。細かい直しで 2〜4 倍速くしたが、評価 50 件で約 24 ms、300 件で約 110 ms（Xeon 2.1 GHz の計測）。案:
1. **点数付けを D1 の SQL に移す**: 利用者の人ごとの値を表に書いておき（評価を書くたびに更新）、rec_credit と結んで公演ごとの上位 3 人・下位 3 人・種類の平均を SQL（窓関数）で出す。D1 で待つ時間は CPU に数えない。代わりに D1 の読み取り行（無料 1 日 500 万行）を使う。Python の参照実装と round6 の一致をどう保つかが難しい
2. **点数を付ける人数に上限**（|値| の大きい順に 400〜600 人）: いちばん簡単。小さい値の人は上位 3 人にほとんど入らないので順位はほぼ変わらない見込みだが、測ってから。試験の作り物の利用者は上限より少ないので Python との一致は保てる
3. **書くときに計算**: 評価・興味ありを書く要求で人ごとの値を更新して保存し、画面の要求では値を読むだけにする
4. **計算を 2 回の要求に分ける**: 1 回目で点数、2 回目で束ね・会場（それぞれ 10 ms 以内）
どれも順位や D1 の使い方が変わるので、起案者に選んでもらう。おすすめは 2（すぐ・小さい）を入れ、1 を調べる。

2026-10-18 追記（起案者「進めて」で案 2 を試した）: **点数を付ける人数の上限は効かなかった。** 上限 500／800／1,500／なしで CPU はほぼ同じ（評価 300 件で 120／94／114／120 ms、揺れの範囲）。一方で順位は変わる（評価 300 件の上位 15 件の重なりが上限 500 で 40〜93%、1,500 で 93〜100%）。効かずに順位だけ変わるので入れなかった。
評価が多いときの重さは、点数を付ける人数ではなく**裏の答え合わせ（reco-gate.chooseVariant）**だった（評価 300 件で CPU の 37%）。答え合わせは、過去の区切りごとに personValues を 20〜40 回計算し直す。
直したこと（screen-v30、結果は変えない）:
- personValues: 評価 1 件ごとの人の鍵を、評価の行ごとに 1 回だけ作って覚える（WeakMap）。同じ尺度の中の順位を、全件比べ（n²）から値ごとの数へ
- 答え合わせの結果を控えに残し、評価が変わらないまま控えが捨てられたとき（お気に入り・興味ありを押した）は使い直す（評価 30 件以上のとき）。試験で、使い直しても計算し直しても同じ一覧になることを確かめた
効果（揺れが大きい。別の作業が同時に動いていた）: 評価 300 件で 110 → 約 93 ms、興味ありを押したあとの計算し直しでは約 72 ms。
残り: 案 1（点数付けを D1 の SQL に移す）か案 3（書くときに計算）でないと、評価の多い人は 10 ms に収まらない見込み。
