# 利用者データのバックアップ・復元検証

2026-10-13（日本時間）。実装、テスト、レビューを別担当とし、実装完了後に変更後テスト、その完了後に最終レビューを行った。

## 実装と独立検証

`tools/taguri/state_backup.py` に、停止中の認証DB・評価DB・pepperを一組で保存／復元するCLIを追加した。SQLite backupで確定済みWALと追加テーブルを含め、integrity・schema・参照整合性・鍵形式・ハッシュを検査する。復元先の既存データを上書きしない。原本は削除せず、結果ログには秘密や原文を出さない。

新規 `test_state_backup.py` は21項目成功。実際の復旧コード・セッション・評価・感想の復元、追加テーブル、空の復元先、既存先拒否、失敗時原本保護、権限、破損DB・不正鍵・不正manifest・リンク拒否を確認した。

| 既存回帰 | 実行数 | 結果 |

| 保存 | 36 | 成功 |
| 推薦 | 34 | 成功 |

件数には既存HTTP検査の再実行が含まれる。既存 `test_digest.py` の見出し期待値不一致は今回の対象外で、全リポジトリの全試験成功を意味しない。

テスト担当が [GitHub Actions run 38282498771](https://github.com/island-6848/taguri-demo/actions/runs/38282498771) のコミット `5b7e639` と全step成功を独立確認した。ローカルでsocket権限により実行できなかったpolite_httpもCIで成功している。

最終レビューは公開を止める欠陥なしと判断した。全writer停止という前提、同時点のsnapshotの範囲、原子公開、既存先保護、秘密の非出力、既存機能・新しいテーブルへの影響を確認した。

## 公開環境の結果と未完了事項

公開 `/api/health` は `state-storage-v1`・`storage.mode=temporary` を返した。Renderプラグインの追加とユーザーによるアカウント接続完了は確認済みだが、この会話にはRenderサービスを操作する機能が提供されていない。

公開サービスの有料ディスク作成、設定変更、既存入力の退避、再起動／再デプロイ後の履歴保持、公開環境でのバックアップ復元は未実施。ディスク追加自体が再デプロイするため、旧入力の退避を先に行う。準備PRをマージするだけでも公開先の自動再デプロイを起こし得るので、今回はPRとして用意し、公開環境の変更を先行させない。

停止フラグは操作者の確認で、他プロセスの停止を自動検知しない。DBごとの30秒期限は大きいDBで失敗し得る。バックアップの暗号化・別ホスト転送・定期保持は未実装。保存先を設定しただけで永続性や復旧成功を保証しない。

設定・退避・再起動・復元の実施手順は [運用文書](demo-state-storage.md) を参照する。
