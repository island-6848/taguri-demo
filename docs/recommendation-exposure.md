# 推薦の取得・接触ログ

2026-10-12。推薦の順位・見た目・既存の持ち主用 `presented` 集計を変えず、取得と画面内への接触を別に記録する。

## 定義

- **提示スナップショット**：サーバが推薦HTMLを生成した時点の、認証済み利用者ID、公演ID、表示順位、地域、生成時刻、推薦方式版、接触定義版。題名・感想・推薦理由本文・認証トークン・復旧コードは保存しない。
- **取得**：サーバが推薦応答を生成またはキャッシュから返す処理に入った記録。`recommendation_fetches.received_at` はサーバ時刻であり、命名上 received でも、ブラウザでの受信完了を証明しない。先読み後に別画面へ移る場合も取得に含まれる。
- **訪問**：ブラウザに推薦画面を差し込むごとに作るランダム `visit_id`。SPAキャッシュからの再訪は取得を追加せず、別の訪問になる。ブラウザの戻るキャッシュ復元も別訪問。
- **接触**：推薦カードの主要領域の面積50%以上が、フォアグラウンドで連続1,000ms画面内にあること。ポスターの読込が成功した場合はポスター画像、画像がない/読込失敗の場合は題名 `h3` を主要領域とする。画像読込中は数えない。ポスターが縦長で画面内に半分入らなければ数えない。

非表示タブ、画面移動、pagehide、復旧コード画面・開いているdialog・`aria-modal=true` のモーダルでは観測とタイマーを止める。復帰時は1秒を数え直す。同一利用者・訪問・公演の接触はDBのユニーク制約でも一度だけ記録する。カード全体は長くなるため接触判定に使わない。

**接触は読んだこと・ポスターを注視したことの証明ではない。** 50%・1秒の判定はブラウザ側で行い、サーバは画面の幾何学的な状態を検証しない。 他のウィンドウによる遮蔽、画面内の一般要素による部分的遮蔽は判別しない。無反応を嫌いという学習信号に使わず、この実装では推薦への補正に一切使用しない。

## APIと認証

既存の利用者解決、公開版のOrigin/JSON制限、ローカルの起動トークン検査を通る。クライアントの利用者ID・順位・時刻は受け取らない。

| API | 正確なJSON項目 | 役割 |
| --- | --- | --- |
| `POST /api/recommendation/visit` | `presentation_id`, `visit_id`, `source` | 訪問開始を冪等に記録 |
| `POST /api/recommendation/contact` | `presentation_id`, `visit_id`, `stage_id` | 登録済み候補への接触を冪等に記録 |

`source` は `network` / `cache` / `local` / `fill` の列挙値。IDは検証し、未登録提示、他の利用者の提示、未開始訪問、提示にない公演、余分な項目は400で拒否する。認証失敗は既存403等に従う。訪問開始の保存成功後にだけ接触を送る。

補充カードは既存の `len(shown)+1` という表示順位を維持し、別の `kind=fill` スナップショットへ登録する。同じ画面の `visit_id` を引き継いで計測する。既存 `shown` に由来する番号は画面上の通し番号であり、母集団全体の順位を示さない。

## 保存先と停止時の挙動

専用SQLite DB `state/recommendation_exposure.db`（リポジトリルートからの絶対パス）に保存する。`TAGURI_STATE_DIR` が設定されている場合はその保存領域内の `recommendation_exposure.db` を既定とする。`TAGURI_EXPOSURE_DB` の明示指定を最優先とし、別の保存先を設定できる。`state/` はGit管理から除外する。既存 `ratings.db` と認証DB、`presented` は変更しない。

クラウドのカタログ更新は `data/` を作り直すため、ログはその外へ置いた。ただし**永続ディスクを指定しないホスティング環境では再起動・再デプロイで失われる**。長期評価に使うには永続ディスクのパスを環境変数で指定する。ローカルは同じパスで再起動後も維持する。

起動時のDB作成失敗、提示の登録失敗、取得/接触の保存失敗は推薦表示・反応を止めない。APIの保存失敗は `{ok:false,disabled:true}` を返す。ネットワーク失敗は黙って捨て、画面のエラー表示を増やさない。再送キューはなく、オフライン終了・ログ障害中の欠測、提示登録後に取得保存だけ失敗する孤立スナップショットも起こりうる。ログ件数を利用者行動の完全な全数とは扱わない。

推薦APIは毎回本人の保存状態から新しい提示を作る（サーバの推薦HTMLキャッシュは使わない）。計測APIはサーバとSPAの画面キャッシュ失効対象から除外し、計測のために推薦計算をやり直さない。SPAの断片キャッシュ再表示は別訪問として記録する。

既存の運用ログには計測APIの成功も `write_result / operation=other` として記録される。これを評価・感想の保存件数には数えない。専用の接触ログと運用ログの粒度は異なる。DBの保持期限・集計管理画面・CSVエクスポート・公演への反応との自動結合は今回の対象外。

## 実装と検証観点

- 保存/検証：`tools/taguri/recommendation_exposure.py`。
- 認証API、提示/取得/補充の登録：`tools/taguri/serve.py`。
- 主一覧だけの提示マーカー：`tools/taguri/app.py`。追跡・見送りなど別束は観測しない。
- 共通観測器：`web/recommendation-exposure.js`。公開SPAとローカルHTMLで同じ処理を使う。IntersectionObserverがない場合は接触を記録しない。
- 各画面再訪/補充：`web/app.js` とローカルの `SCRIPT`。

独立テスト担当は、50%と1秒の境界、途中離脱/非表示/モーダル、戻る/キャッシュ再訪、補充、画像の読み込み/失敗、同一訪問での重複、利用者分離、未登録IDと余分な項目の拒否、ログ故障、既存キャッシュとowner集計への非干渉を確認する。実装完了後に実行し、最終レビューはテスト完了後に行う。
