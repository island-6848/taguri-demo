# Cloudflare完全移行・利用者登録の検証

作成日: 2026-10-12（日本時間）  
対象: `cloudflare-d1-preview`、コミット `b889151d614ce65320bab15db663ce95e6e94e59`  
方針: 元のデザイン・操作を維持し、費用を最優先にWorkers Free + D1へ移行する。

## 1. 結論

**完全移行は未完了。現時点でRenderを停止すると、元の画面の機能が使えなくなる。**

Cloudflareには元のフロントエンドとD1の簡易版APIがある。しかし、公開中の元UIはRenderで画面を生成し、Render側のSQLiteに保存している。D1への保存に切り替わったわけではない。

完全移行には、①元の全機能のバックエンド移植、②欠損のないデータ移行、③認証と利用者IDの統合、④公演情報の更新・画像・推薦処理の移行、⑤公開環境での検証と復元確認が必要。

利用者はCloudflare・GitHub・Supabaseのアカウントを作る必要はない。現在の方式はメールアドレスとパスワードを登録せず、初回アクセスで利用者を作り、Cookieと復旧コードで継続利用する方式。無料優先かつ元の操作を維持するなら、この方式を継続するのが第一候補。

## 2. 現在の構成と保存先

| 項目 | 現状 | 判定 |
|---|---|---|
| 元のHTML/CSS/JS・チュートリアル・D3・動画 | Cloudflareの静的アセットで配信 | 移行済み |
| 元の17画面のHTML生成・操作API | Workerから固定先Renderへ転送 | 未移行 |
| 元UIで追加する観劇記録・評価・感想等 | Render側SQLiteへ保存 | 未移行 |
| D1の記録・お気に入り・三択反応・復旧 | 独立した簡易版APIで実装 | 実装済み・元UIとの統合は未完了 |
| 簡易版で保存済みのデータ | `/migration-data/`、`/migration-api/`に保持 | 元UIとは別の利用者・保存先 |
| 元UIのJSON/ZIP書き出し | ブリッジで503を返す | 利用者別の実装が必要 |
| 公演カタログ・元の推薦・画像 | Render／非公開データに依存 | 未移行 |

設定は [wrangler.jsonc](../../cloudflare/wrangler.jsonc) の `ORIGINAL_UI_BRIDGE=true`。
[original-ui.js](../../cloudflare/src/original-ui.js) が転送し、[worker.js](../../cloudflare/src/worker.js) がD1簡易版APIを担当する。

元UIのCookieは `tg_session`、D1簡易版は `taguri_session`。相互にログインできず、記録も自動統合されない。CloudflareのURLが表示されているだけでは、保存先の移行を確認したことにならない。

## 3. 完全移行に足りないもの

優先度P0はRender停止前に必要。P1は一般利用者の継続利用を案内する前に必要。

| 優先度 | 残作業 | 完了条件 |
|---|---|---|
| P0 | 元UIの全画面・操作APIをRender依存から外す | 17画面と全操作をWorkers側で実行でき、Renderを遮断しても動く |
| P0 | 元のデータ構造をD1へ移植 | 複数回観劇、回ごとの評価、動機、券、反応理由、除外、統合、手動クレジット等を保持できる |
| P0 | 実稼働データの安全なバックアップ・全件移行 | 利用者ごとの件数・内容・関連付けを移行前後で照合し、重複・欠損がない |
| P0 | 旧利用者と新利用者の対応付け | 旧復旧コード／既存セッションから本人の記録へ移行でき、他人の記録へアクセスできない |
| P0 | 簡易D1版の保存済み記録を元UIへ統合 | 現在のD1利用者が同じ記録を元UIで読み書きできる |
| P0 | 公演検索・推薦・分析・カレンダー等の移植 | 元版と同じ入力で必要な表示・結果が得られる。差がある場合は仕様として明記 |
| P0 | カタログ更新と画像の配信 | Render・非公開S3の実行時取得に頼らず、必要な情報を更新・配信できる |
| P0 | 公開環境で保存・復旧・再デプロイを検証 | 再読み込み、端末変更、セッション切れ、再デプロイ後も記録が残る |
| P0 | バックアップと復元・切り戻し | 保存したバックアップから別の検証DBへ復元し、内容を照合できる |
| P1 | 利用者単位の書き出し・削除 | 本人の全記録だけを出力・削除できる。全利用者の一括出力を公開しない |
| P1 | 新規登録・復旧・端末追加の制限 | 試行回数制限、期限、一回使用、登録停止を実装し、超過時の案内を確認 |
| P1 | デモと実利用を分離 | 新しい実利用者に、所有者の観劇履歴やお気に入りを本人の記録として入れない |
| P1 | 上限と運用の整備 | アカウント数・保存量・無料枠を監視し、上限到達時に説明を表示する |
| P1 | 利用案内・規約の更新 | 保存先、復旧、削除、外部送信、Gmailの対応範囲が実装と一致する |

### 現在の変換スクリプトで足りない範囲

[convert_records.py](../../cloudflare/scripts/convert_records.py) は利用者IDを指定した読み取り専用変換に対応するが、作品の初回日・時刻・会場・評価・感想などの部分移行である。**これだけで完全移行とは扱えない。** 複数回観劇や回別評価、動機、券、除外・統合、反応理由、手動情報などを別途移植する必要がある。

[convert_catalogue.py](../../cloudflare/scripts/convert_catalogue.py) は公開情報を選別して候補に取り込む。所有者の個人的な推薦理由・順位・感想を他の利用者へ配布するためのものではない。お気に入り照合はあるが、元の順位付き統計推薦は未移植。

### 実データと認証の確保

運営側が、実稼働の観劇・反応・券等のDB、認証DB、公演カタログ、必要な画像・手動設定、旧認証のpepperを安全な保存先へ確保する必要がある。公開リポジトリのデータだけでは、実稼働利用者の全記録を検証できない。

旧認証はscryptとpepper由来の利用者ID、新認証はランダムIDと復旧コードのハッシュで方式が異なる。旧コードをそのまま新コードとして使える実装にはなっていない。旧方式を検証できる移行処理を設けるか、旧セッションで本人確認して新コードを発行する等、移行経路を実装・検証する。

旧Cookieは別ドメインへ自動で引き継がれない。移行案内には旧サイトでの復旧コードの控え方と、新サイトで本人の記録を引き継ぐ操作を含める。

旧起動処理 [serve_cloud.py](../../tools/taguri/serve_cloud.py) はS3アーカイブ展開前に `data/` を削除する。元UIも再起動時のリセットを案内しており、現行保存の永続性を前提にできない。移行直前のバックアップと、切替中の書き込み停止または差分移行が必要。

### 移植方式の判断

元版はPythonのHTTPサーバー・ローカルSQLite・ファイル・スレッド・サブプロセスを使う。Python自体はWorkersで対応しているが、元のサーバーをそのまま実行できるという意味ではない。D1アクセス、画面生成、長時間処理を実行環境に合わせる必要がある。

無料枠でのCPU時間を測り、重い推薦・集計は事前計算や共通データ更新へ寄せる。元のフロントエンドを維持したままAPIの内側を移植し、別デザインへの置き換えは行わない。

## 4. 今後の利用者登録と利用の流れ

### 現在できること

1. 公開URLを開くと、元UIのデモでは初回に利用者とセッションが作られる。
2. 初回に表示される復旧コードを、本人の安全な場所へ控える。一度しか表示されない。
3. 同じブラウザではCookieで継続利用する。
4. 別端末やCookie削除後は復旧コードを使う。元版には期限付き6桁の端末追加コードもある。
5. お気に入り、公演、観劇記録、評価、感想を登録する。

**現段階はデモであり、再起動によるリセットの制約が残る。長期保存が保証された本番サービスとして案内する段階ではない。**

画面の「登録」は公演情報の登録を指す場合があり、メールアドレスを登録するアカウント作成画面とは異なる。

### 完全移行後の推奨フロー（未実装部分を含む）

1. 「初めて使う」で本人の空の保存領域を作る。既存利用者には「記録を引き継ぐ」を案内する。
2. 復旧コードを控える。コードを誰かへ渡すと本人の記録へアクセスされるため、共有しない。
3. お気に入りや観劇記録を入力し、推薦・カレンダー等を利用する。
4. 別端末では復旧コードまたは端末追加コードを使う。
5. 必要に応じて本人の記録を書き出す。利用をやめる場合は本人のデータを削除できるようにする。

メールアドレス・パスワード登録、確認メール、パスワード再設定、Googleログインは現在実装されていない。採用するなら追加開発と運用が必要であり、無料で継続利用するための必須条件ではない。

| 利用者が用意するもの | 必要性 |
|---|---|
| ブラウザとインターネット接続 | 必須 |
| 復旧コードの保管先 | Cookie削除・別端末利用・復旧に必要 |
| Cloudflare／GitHub／Supabaseアカウント | 不要。運営側が管理する |
| Gmailアカウントと接続 | 基本利用には不要 |
| 有料契約・APIキー | 基本利用には不要 |

コードとCookieを両方失った場合の本人確認による復旧は用意されていない。メールアドレスを取得しない方式では、運営が問い合わせだけで復旧できると約束しない。

### 認証で残っている差

D1簡易版のセッションは30日、旧版は発行から365日を上限とする。頻繁な再入力を避ける継続・更新方針を決め、実装する。D1には旧版の6桁端末追加フローがない。

D1簡易版は100アカウント、1人500記録・200お気に入り・500反応というプレビュー上限がある。一般公開の人数と用途に合うか確認する必要がある。

`ALLOW_REGISTRATION=false` はD1側の新規登録にだけ効く。**現在のブリッジ経由の旧版自動登録を止める設定ではない。** 登録停止を運営手段として使う前に、元UIの経路も含めて統一する。

## 5. 各利用者のGmail取り込み

チャットに接続したGmailからデモ用購入情報を抽出することと、Webアプリの各利用者が自分のGmailを接続することは別の機能。前者の接続権限を後者へ流用できない。

元サーバーのメール取り込み [serve.py](../../tools/taguri/serve.py) は `_owner_only(user_id)` で制限され、サブプロセスを起動する。各利用者向けのGmail接続としては未実装で、Workersへそのまま移せない。

既存の [セキュリティ規約](../000007-taguri-security-rules.md) E2・O4では、Gmail連携を公開v1から除外している。今回のデモ抽出依頼が、全利用者向け連携の実装・公開完了を意味するわけではない。

無料を最優先にするなら、まず手入力と利用者単位のJSON取り込みで利用できる形を完成させる。メールファイル取り込みを追加する場合も、別途形式・抽出・個人情報の扱いを実装する。

将来Gmail自動連携を追加する場合は、運営側がGoogle OAuth設定、必要スコープの審査条件、利用者別トークンの保護・更新・解除、抽出と重複防止、本文の保存方針を整える。利用者はその後にGoogleの同意画面で自分のメールの読み取りを許可する。審査・セキュリティ評価等の適用条件と費用は導入時に公式情報で再確認し、無料と決めつけない。

## 6. 運営側が行う切替手順

1. 全機能・API・保存項目の一覧を作り、元UIの入出力を固定する。
2. 実稼働データと認証のバックアップを取得し、非公開の検証環境へ復元する。
3. 元UIにつながるD1側API、旧利用者の移行経路、公演情報更新を実装する。
4. 利用者ごとの記録・関連データを移し、件数と内容を照合する。再実行しても重複しないことを確認する。
5. PC・スマホで17画面と全操作を検証する。新規利用者・既存利用者・簡易D1版利用者を別々に検証する。
6. 公開先で再デプロイ、復旧、利用者間分離、書き出し・削除、無料枠の使用量を確認する。
7. 最終差分を移し、ブリッジを外してRenderへの通信がないことを確認する。
8. 復元と切り戻しを確認した上で利用者へ新URLを案内する。旧データの保管期間を決め、最後にRenderを停止する。

運営側のCloudflareアカウントとGitHub連携は既に利用中。現在のビルド設定はルート `cloudflare`、デプロイコマンドは以下。**DBを新規作成し直す必要はない。**

```sh
npx wrangler d1 migrations apply taguri-demo --remote && npx wrangler deploy
```

アカウント秘密情報、APIトークン、pepper、実利用者のDBを公開リポジトリや検証文書へ記載しない。

## 8. 無料継続の条件

Workers FreeとD1から始め、`workers.dev` を利用する。Supabase、有料ドメイン、R2、外部LLM、確認メール配信はこの構成の必須要素ではない。

ただし無料枠には使用量と実行時間の上限がある。「無制限・永久無料」を保証する構成ではない。重い処理を毎回実行しない設計、DBのインデックス、公開情報だけのキャッシュ、利用者別APIの非共有、不要セッションの整理、上限時の案内を整える。画像容量やカタログ更新の実際の費用も移行前に確認する。

公式確認先:

- [Workers料金・無料枠](https://developers.cloudflare.com/workers/platform/pricing/)
- [D1料金・無料枠](https://developers.cloudflare.com/d1/platform/pricing/)
- [Python Workers](https://developers.cloudflare.com/workers/languages/python/)
- [Gmail APIのOAuthスコープ](https://developers.google.com/workspace/gmail/api/auth/scopes)

## 9. 判定

現時点の判定は **「元のフロントエンド復元と部分的なD1移植は完了。Renderからの完全移行と一般利用者向け継続運用は未完了」**。

次に実装すべき中心は、元UIのAPIと全保存項目をD1へつなぎ、既存利用者の認証・記録を欠損なく引き継ぐこと。利用者が新しいクラウドサービスを契約する作業は不要。
