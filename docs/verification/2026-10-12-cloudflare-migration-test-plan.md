## 判定と環境

元のデザインと操作、Renderへの実行時依存解消、D1の全保存項目、利用者間分離、復旧・端末追加、推薦・検索・画像、本人だけの出力・削除、秘密を含めないログが対象。[移行検証文書](2026-10-12-cloudflare-migration-and-onboarding.md)の未完了事項を基準にする。

検証DB・利用者は合成データだけを使用する。公開URLへ登録・書き込み・削除を行わず、既存利用者や実DBをテストのために変更しない。全移行の実データ照合と公開環境の復元・再デプロイは、別途安全な実データと権限が必要で、ローカル成功だけでは完了と判定しない。

調査時点でNode v24.19.0、Python 3.12.14がある。`cloudflare/node_modules`は未配置。Wrangler、Playwright、Chromiumと必要依存の準備が必要。実稼働データ、旧pepper、認証DB、Cloudflare公開環境の権限は未提供。

## Python互換方式の追加条件

実装担当から示された方式は、全`user_id`テーブルを利用者単位のsnapshotとしてD1へ保存し、リクエストごとのSQLiteへ復元して元のPython Handlerを再利用するもの。確定した実装仕様ではなく、追加で必要な確認を以下に記す。

- snapshot → materialize → capture の往復で全列・件数・値・関連が一致する。NULL、Unicode、複数回観劇、同じキーを持つ別利用者を含める。
- 同じrevisionを読んだ同時更新では一方だけがCAS保存に成功し、競合した更新は明示的に拒否または安全に再適用される。成功応答の後で片方の更新が消失しない。
- 入力拒否、DB例外、Handler例外、CAS競合の各経路で、一時DB・グローバルDBパス・ユーザー状態が片付けられ、次の別利用者へ漏れない。
- 元HandlerのCookie、redirect、status、Content-Type、JSON/HTML本文を捕捉し、元UIが必要なレスポンス契約を維持する。
- subprocess、socket、threadを使う処理が残っていないか、非対応APIが何かを明確にする。
- CPythonとfakeD1の合格は、Pyodide/workerd実行、D1の実トランザクション/競合、無料枠CPU・実リクエスト互換性の合格とは別に記録する。

追加の無料枠判定: snapshotに96件を保存する操作は、D1 Freeの1 invocationあたり50 queries以内に収まることをquery-count付きfakeD1で確認する。行ごとにINSERTを96回行う実装は不合格。fakeD1の数え方と実D1の計上差は実行環境で別途確認する。

## owner移行の追加設計（実装freeze待ち）

旧`local`持ち主の明示移行を別経路として検証する。通常guestは同じIDのまま保持し、フラグなしのowner移行と任意guestの異IDへのmergeは拒否する。明示owner-transferだけが新private targetへ全表の所有列を再割当し、主キー由来rowkey・checksum・countを移行後の値で再生成する。共有表はinventoryとして残し、自動公開・コピーしない。

新targetへ投入後の全表値を読戻し、既存target衝突はusersからsnapshot rowsまで原子的にrollbackする。復旧コードはmanifestや標準出力・ログに含めず、別0600ファイルにだけ保存する。コードhashとtarget accountの対応、既存出力ファイルの非上書き、途中I/O失敗時の片方だけ残る状態も確認する。

GitHub CIで実Python Workers/DOを試す最小案は、依存sync→source/public build→直接Wrangler→独立local D1へschema適用→local dev起動→readiness polling→合成guestと17screen・保存・復旧・端末追加・削除・exportをHTTP実行→cleanupとログartifact。既存JS版のworkerd成功やPython版dry-runだけをPython DO runtime成功に数えない。追加ネット許可を必要とするローカル準備は行わず、ここでは計画に留める。
