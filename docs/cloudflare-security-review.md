# Cloudflare版のセキュリティ点検（2026-10-13）

対象は `cloudflare-d1-preview` ブランチ（PR #5、`641cc17`）のCloudflare Worker版である。具体的には次のとおり。

- ログイン：Firebase・パスキー・復旧コード
- 記録API と D1
- 元の画面をRenderへ渡す橋渡し
- 静的ファイル
- デプロイの流れ

**点検のやり方。** コードを読み、自動テストを確かめ、`npm audit` で依存を監査した。本番環境への攻撃試験（ペネトレーションテスト）はしていない。Cloudflare・Firebase・Google Cloud・GitHubの管理画面の設定は見ていない。設定に関わる項目は「要確認」とし、検証項目に入れた。

## 結論

- **ログインと記録の扱いの作りは堅い。** 復旧コード・セッション・Firebase・パスキーは、どれも推測できない長さの乱数か、署名の検証に頼っている。DBにはハッシュか公開鍵しか置かない。
- **公開前に直すべき点は、作りよりも運用の側にある。**
  - アカウントの完全削除が無い（S1）。
  - pushがそのまま本番に出る（S2）。
  - 登録口に回数制限が無い（S3）。

## 問題点

重大度：**高**＝公開前に必須、**中**＝公開前に直したい、**低**＝公開後でよい、**情報**＝知っておくこと。

| ID | 重大度 | 内容 | 起きうること | 対策 |
|---|---|---|---|---|
| S1 | 高 | **アカウントと記録を完全に消す機能が無い**（セキュリティ規約R7）。ログアウトはあるが、D1の記録・パスキー・Firebaseとの結び付けが残る | 本人の求めに応じて消せない。利用規約・個人情報保護法の上で問題になる | 本人確認（ログイン直後・5分以内）のうえで、`users` を消す（外部キーで記録・セッション・パスキーも消える）。Firebase側の利用者も消すよう案内する |
| S2 | 高 | **PRのブランチが本番として扱われている**。`cloudflare-d1-preview` へのpushだけで、Workers BuildsがD1の移行と本番デプロイを行う。CIはデプロイと並行して走るので、テストに落ちたコードも本番に出る | 書き込める人なら誰でも、レビューなしで本番を変えられる。壊れた移行がそのまま本番のD1に入る | 本番の反映元をmasterにする。masterはPRのレビューと必須チェック（check・feedback-loop）を通したものだけにする。ブランチはプレビュー環境に出す |
| S3 | 中 | **登録口に回数制限が無い**（`/api/register`・パスキーの新規登録・Firebaseの新規登録）。今は「アカウント100件まで」の上限があるが、上限に達すると誰も登録できなくなる。パスキーのチャレンジは全体で1000件までなので、連打されると5分間、全員がパスキーでログインできなくなる | 登録の妨害、ログインの妨害（DoS）、D1の書き込み枠の消費 | CloudflareのRate Limitingルール（IPごと）を `/api/register`・`/api/auth/*` に掛ける。必要ならTurnstileを足す。チャレンジの上限はIPごとに持つ |
| S4 | 中 | **依存の版が固定されていない**。`package-lock.json` が無く、間接的な依存（`@peculiar/*` など）は `^` で動く。同梱した部品（`public/vendor/firebase-login.js`・`passkeys.js`）が元のコードから作られたものかを、CIで確かめていない | 依存が乗っ取られたときに、気づかないまま本番に入る | `package-lock.json` をコミットし、CIとWorkers Buildsで `npm ci` を使う。CIで部品を組み立て直し、コミットした物と一致するかを確かめる |
| S5 | 中 | **元の画面のCSPが弱い**。`script-src 'self' 'unsafe-inline' 'unsafe-eval'`（元の画面がインラインのスクリプトを使うため）。サーバーが返すHTMLの断片を `innerHTML` で差し込むので、XSSを防ぐのはPython側のエスケープだけになっている。Renderへの橋渡しの応答（`/api/screen/*`・`/img/*`）にはCSPが付かない | Python側のエスケープ漏れが1つあれば、そのままスクリプトが動く | インラインのスクリプトを外部ファイルにし、`unsafe-inline`・`unsafe-eval` を外す（またはnonceを使う）。橋渡しの応答にもCSPを付ける |
| S6 | 低（要確認） | **FirebaseのAPIキーに制限が付いているか分からない**。キーは公開してよい値だが、制限が無いと他のサイトで使い回され、メールリンクの送信などの枠を消費される | 送信の枠の消費、迷惑メールの踏み台 | Google Cloudでキーに「ウェブサイト（Workerのドメインと `taguri-97959.firebaseapp.com`）」と「Identity Toolkit API・Token Service API だけ」の制限を付ける |
| S7 | 低 | `/api/logout` のCookieの読み取りが先頭一致になっていない（他の箇所は `sessionCookie()` で厳密に読む）。`/api/register`・`/api/recover` は、それまでのセッションを消さない | 実害は小さい（別名のCookieを置ける相手はいない）が、作りが揃っていない | `sessionCookie()` に揃え、`startSession` に古いCookieを渡す |
| S8 | 低 | 期限切れのセッションと使われていないアカウントを、定期的に消していない（そのアカウントがログインしたときにしか掃除されない） | 不要なデータが残り続ける（データの最小化） | Cron Triggerで期限切れのセッション・チャレンジを毎日消す。長く使われないアカウントの扱いを決め、利用規約に書く |
| S9 | 低 | メールリンクでログインするとき、メールアドレスがリンクを開くまで端末の `localStorage` に残る（リンクを開かなければ残り続ける） | 共用端末で、他人にメールアドレスを見られる | 保存した時刻も持ち、1時間で消す |
| S10 | 情報 | パスキーはドメイン（今は `…workers.dev`）に結び付く | 独自ドメインに移ると、それまでのパスキーが使えなくなる | 移る前に告知する。Google・復旧コードでログインして登録し直す手順を用意する。本番では `WEBAUTHN_RP_ID` を固定する |
| S11 | 情報 | 開発用の依存 `firebase@13.0.0` の中の `@grpc/grpc-js` に、`npm audit` で高4件。同梱した部品には含まれない（Firestoreでしか使わない）ことを確かめた | 利用者には影響しない。開発環境の衛生の問題 | Firebaseを上げられるときに上げる |
| S12 | 情報 | 二重になっていたD1移行のワークフローは消した。しかし、GitHubのSecret `CLOUDFLARE_API_TOKEN` とCloudflareのAPIトークンはまだ残っている | 使われない鍵が残っている | 両方を削除する（持ち主の作業） |
| S13 | 要確認 | D1のバックアップと復元を確かめていない | 移行の失敗や誤操作で記録を失う | D1のTime Travel（巻き戻せる期間）を確かめ、一度復元を試す |

| 記録API | `test/worker.test.js` | 他人の記録を読めない・変えられない。別のオリジンからは書けない。不正な入力・期限切れのセッション |

| パスキー | `test/passkey.test.js` | 新規作成→ログイン。既存アカウントへの追加。偽のオリジン・RP ID・本人確認なし・別の鍵・ユーザーハンドルの不一致。チャレンジの再利用と期限切れ。複製の検知。他人のアカウントへの追加の横取り。削除。チャレンジの上限 |

### 足すべき自動テスト

| ID | 内容 | 合格の基準 |
|---|---|---|
| T1 | アカウント削除（S1を作ったら） | 削除後、D1のどの表にもその利用者の行が無い。同じGoogle・パスキー・復旧コードでは戻れない |
| T2 | 部品の再現（S4） | CIで `npm run build:login` をやり直し、コミットした `public/vendor/*.js` と一致する |
| T3 | 依存の監査 | CIで `npm audit --omit=dev` が0件 |
| T4 | ログアウトとセッション（S7） | 復旧コード・新規登録のあと、それまでのCookieが401になる |
| T5 | 元の画面のXSS | 題名・感想・お気に入り名に `<script>`・`"><img onerror=…>` を入れた画面を、ブラウザのテストで開いてもスクリプトが動かない |

### 本番環境で手で確かめること

| ID | 内容 | 合格の基準 |
|---|---|---|
| P1 | ヘッダ | `/login`・`/migration-data/`・`/api/state` の応答に、想定のCSP・`X-Frame-Options`・`nosniff`・`no-store` が付いている |
| P2 | Cookie | ブラウザの開発者ツールで、`taguri_session` が `HttpOnly`・`Secure`・`SameSite=Strict` |
| P3 | 本物のパスキー | iPhone（iCloudキーチェーン）とAndroidかWindowsで、新規作成→ログアウト→ログインができる。別の端末に同期されたパスキーでもログインできる |
| P4 | Google・メールリンク | 両方でログインできる。メールリンクを別のブラウザで開くと、メールアドレスを聞き直す |
| P5 | Firebaseの設定（S6） | 承認済みドメインがWorkerのドメインと必要なものだけ。メール列挙保護がオン。パスワードでのログインがオフ。APIキーに制限がある |
| P6 | Cloudflareの設定 | Rate Limitingルールが効いている（S3）。Workersのログに、トークン・メールリンクのコード・Cookieが残っていない |
| P7 | GitHubの設定 | 本番の反映元が保護されたブランチである（S2）。使わないSecretが残っていない（S12） |
| P8 | D1の復元（S13） | Time Travelで、前の時点に戻せることを試した |

## 持ち主にお願いすること

1. GitHubのSecret `CLOUDFLARE_API_TOKEN` と、CloudflareのAPIトークン `taguri-d1-migrate` を削除する（S12）
2. FirebaseのAPIキーに制限を付ける（S6）。済んでいれば教えてもらう
3. 本番の反映元をどうするかを決める（S2）。PR #5をmasterにマージするかどうかと一緒に決めるのがよい
