# デモから実サービスへ：リリースまでにやること・検証項目

2026-10-12 時点の master（`30f4293`）のコードと `docs/` の記録を読んで洗い出した。
**実際の公開環境（Render・S3・Cloudflare の管理画面）は見ていない。** 公開環境の状態は、既存の記録に書かれている範囲で扱う。

## 0. いまの位置

| 観点 | いま（デモ） | 実サービスで必要なこと |
|---|---|---|
| 想定する利用者 | 就活のリクルーター。数分触って帰る | 継続して記録をためる一般の利用者 |
| データの重み | 消えても困らない（見本の96件を毎回入れる） | **消えたら信頼を失う**本人の観劇履歴 |
| 保存 | `TAGURI_STATE_DIR` で保存先を分ける作りはある。**公開先の永続ディスクは未設定・未検証**（[保存領域](demo-state-storage.md)） | 永続ディスク、バックアップ、復元の手順 |
| 稼働 | Render の無料枠。休止後の初回は10〜20秒かかる | 休止しないプランと監視 |
| 動作モード | `demo_mode=True`（`serve.py` の「デモ用の共有データセットしか置かない前提」で、合言葉の検査を迂回している） | 「本番モード」としての前提の書き直し |
| 規約 | 「個人のポートフォリオ規模を前提」、データ保護法は**未検討**（[セキュリティ規約 R8](000007-taguri-security-rules.md)） | 利用規約・プライバシーポリシーの確定 |
| ホスティングの移行 | Cloudflare 版は PR #5 で作業中。Workers Builds は master でも失敗している | どちらで出すかを決め、もう一方を止める |

## 1. リリース前に必ずやること（ブロッカー）

### 1-1. データを失わない

- [ ] **永続ディスクを用意し、`TAGURI_STATE_DIR` を設定する。** （古い案。有料のディスクは使わない〔dec-free-tier-only〕）Render なら有料サービスの persistent disk に置く（[手順](demo-state-storage.md#公開先の設定)）。
- [ ] **バックアップを自動化する。** `ratings.db`・`auth.db`・`auth_pepper.txt` を**同じ時点で**取得し、暗号化して別の場所（S3 の非公開 prefix 等）に世代を残す。いまの実装には含まれていない。
- [ ] **pepper の保管場所を二重化する。** pepper を失うと、全利用者の復旧コードが二度と使えなくなる（`auth.py`）。ディスクとは別の秘密情報置き場にも控える。
- [ ] **SQLite で受け止められる規模かを決める。** 単一インスタンス・書き込みは1本の錠で直列化する作りである（`serve.py` の `Server.lock`）。この作りのまま複数台に増やすことはできない。想定する利用者数を決め、超えたら移行する先（Cloudflare D1 等）を決めておく。

### 1-2. デモ専用の振る舞いを外す

- [ ] **「本番モード」を `demo_mode` から分ける。** いまの `demo_mode` は次をまとめて切り替えている。一つずつ、本番で残すかを決める。
  - 起動ごとの合言葉（`X-Taguri-Token`）の迂回 → Cookie と Origin の検査で置き換えたうえで、本番でも迂回するか
  - 新規訪問者を Cookie なしで即座に登録する動き → 本番でも続けるか（ボットが訪れるたびに利用者が作られる）
  - エラー文を固定文言にする動き → 本番でも残す
- [ ] **見本データの投入をやめる。** 新規利用者に架空の96件（[見本の評価](demo-seed-ratings.md)）が入ったままだと、本人の記録と見本が混ざる。これらの見本は `verdict_source='demo'` で区別されているが、本番では入れない（またはチュートリアル専用の別の場所に置く）。
- [ ] **画面と README から「デモ」の文言を消す。** 「架空の評価」「就活向け」などの説明を、本番向けの案内に差し替える。
- [ ] **持ち主専用の機能（`_owner_only`）が、本番で他人に見えないことを確かめ直す。** 年表・人物の分析・Gmail の取り込みが対象。

### 1-3. セキュリティ規約で「未実装」のまま残っているもの

| 規約 | 内容 | いまの状態（コードで確認） |
|---|---|---|
| **R7** | 復旧コードで自分のデータを完全に削除できる | `auth.delete_user` はあるが、**消すのは認証情報だけ**で、観劇記録・反応・お気に入りは残る。**画面と API が無い** |
| **C15** | 状態を変える POST に CSRF 対策をする | デモモードで Origin の照合と `application/json` の強制はある。独自ヘッダの検証や、本番の Cookie 設定（`SameSite=None` のまま）は見直しが要る |
| E1 | HTTPS | Render・Pages は HTTPS。独自ドメインにする場合は HSTS も |
| E5〜E7 | 非 root 化・SSH の絞り込み・ログのマスク | ログのマスクは実装済み（[運用ログ](demo-state-storage.md#運用ログ)）。EC2 側（カタログ作成）の非 root 化・SSH は未確認 |
| R5 | コードと文書に書いた実例の実名をマスクする | 規約に「公開の障害になっている」と書かれたまま |
| — | セキュリティヘッダ | `Referrer-Policy` 以外（CSP・`X-Content-Type-Options`・`frame-ancestors`）は出していない |

- [ ] R7：記録・反応・お気に入り・券・メモ・認証を一括で消す削除 API と画面を作る（`rate_performances.USER_TABLES`・`feedback`・`auth` のすべて）。
- [ ] C15：本番の Cookie・CORS・CSRF の組み合わせを決めて実装する。
- [ ] セキュリティヘッダを足す。
- [ ] R5：実名の残りを洗い出してマスクする。
- [ ] 上の各項目で `security-rules.md` 冒頭の「既知の不整合」を解消し、規約と実装を一致させる。

### 1-4. 法務・取得元との関係

- [ ] **プライバシーポリシーを作る。** 何を保存するか（記録・感想・お気に入り名）、外部に送るもの（Gemini への送信、CoRich への登録名検索）、保存期間、削除の方法、問い合わせ先を書く。個人情報保護法の範囲と、海外からの利用（GDPR）をどう扱うかを決める（R8）。
- [ ] **利用規約を本番向けに改訂する。** 「ポートフォリオ規模を前提」の文言と、Gmail 機能を凍結している記述を整理する。
- [ ] **取得元の規約を確かめ直す。** CoRich・ステイジーズの利用規約が、公開サービスでの表示（とくに**ポスター画像**と、あらすじの引用）を許すかを確認する。必要なら運営元へ問い合わせて許諾を取る。いまの取得の作法（[取得の方針](crawler-policy.md)）は礼儀の話で、許諾の代わりにはならない。
- [ ] **Gemini API の利用条件を確かめる。** 無料枠では送ったデータが Google の改善に使われる条件がある。感想の抜粋を送る経路（規約 C10 の例外）があるので、**送る内容をさらに絞る**（有料枠には移さない〔dec-free-tier-only〕）。
- [ ] 問い合わせ先と、削除依頼を受ける窓口を用意する（復旧コードを失った人は自分で削除できない）。

### 1-5. 運用

- [ ] **休止しないプランに移す。** 無料枠の休止は、初回表示の10〜20秒の待ちと、カタログの入れ替えのタイミング（[カタログの定期更新](catalog-refresh.md)）の両方に影響する。
- [ ] **死活監視を入れる。** `GET /api/health` を外から定期的に叩き、落ちたら通知する。`storage` が `configured` になっていることも見る。
- [ ] **カタログ作成（EC2）の失敗を通知する。** いまは `journalctl` に出るだけで、止まっても誰も気づかない。
- [ ] **ホスティングの方針を決める。** Render のまま続けるか、Cloudflare（PR #5）に移るかを決める。続けないほうの Workers Builds は連携を外す（いま master のコミットに ✗ が付く原因）。
- [ ] **障害時の手順を書く。** カタログの巻き戻し（`history/` から戻す）、DB の復元、pepper の復元の順番。

## 2. リリース後でもよいが、早めにやること

- 推薦精度の検証（[推薦への接続](user-recommendation-loop.md)には「精度の改善は未検証」と書かれている）。見本と実データを分け、同意を得た実データだけで評価する仕組みを作る。
- 推薦の露出ログ（何を見せて何が押されたか）。利用目的と保持期間を決めてから実装する。
- 応答時間の計測と、利用者数に応じた負荷試験。
- データの書き出し（設定画面の「書き出す」）が本番の保存先でも動くことの確認。
- 再演や別団体の同じ題名の作品を正しく分ける作品 ID。
- Gmail からの取り込み（凍結中の O4・C8・R2）。不特定多数向けにするなら Google の OAuth 審査が要る。

## 3. 検証項目

「合格の基準」を満たしたら ✅ を付ける。**ローカルでの合格と公開環境での合格は分けて記録する**（[独立検証記録](state-storage-verification.md)と同じ方針）。

### 3-1. 自動テスト（毎回）

| # | 項目 | 合格の基準 |
|---|---|---|
| T1 | `tools/taguri/test_*.py` をすべて実行する | すべて通る。**いま `test_digest.py` に見出しの不一致が1件あり、まずこれを直す** |
| T2 | `tools/review/test_*.py` | 実データを要求するものを除いてすべて通る。除いたものは一覧に残す |
| T3 | CI | master への push で T1・T2 が走り、失敗したらマージできない |
| T4 | Cloudflare 版を採る場合 | `cloudflare/` の `npm test` と Workers Builds が通る |

### 3-2. データの保存と復元（公開環境で）

| # | 項目 | 合格の基準 |
|---|---|---|
| D1 | 再起動 | 記録をつけ、プロセスを再起動したあとも、同じ Cookie で同じ記録と推薦が出る |
| D2 | 再デプロイ | D1 と同じことが再デプロイ後にも成り立つ |
| D3 | 復旧コード | Cookie を消したあと、復旧コードで同じ記録に戻れる（D2 の後でも） |
| D4 | カタログの入れ替え | S3 のカタログを更新し、入れ替わったあとも利用者の記録が残る |
| D5 | バックアップからの復元 | 別の環境にバックアップを戻し、D3 と同じ確認が通る（pepper も込みで） |
| D6 | 壊れたカタログ | 件数不足や危ないパスを含むカタログは載らず、前のカタログで動き続ける |

### 3-3. 利用者ごとの分離と削除

| # | 項目 | 合格の基準 |
|---|---|---|
| U1 | 他人の記録 | 利用者Aの評価・感想・お気に入り・興味ありが、利用者Bのどの画面にも出ない |
| U2 | 他人の操作 | Bの Cookie で、Aの `work_key`・`stage_id` を指定した書き込みが拒否される |
| U3 | 持ち主専用の機能 | 一般の利用者が年表・人物の分析・Gmail の機能を開けない（403 か非表示） |
| U4 | 完全削除（R7） | 削除後、DB のどの表にもその `user_id` の行が残らない。同じ復旧コードで戻れない |
| U5 | 見本データ | 本番で新規登録しても、見本の記録（`verdict_source='demo'`）が入らない |

### 3-4. セキュリティ

| # | 項目 | 合格の基準 |
|---|---|---|
| S1 | CSRF | 別のオリジンのページからの POST が 403 になる。フォーム形式（`text/plain` 等）の POST も通らない |
| S2 | XSS | 題名・感想・お気に入り名に `<script>` や `"><img onerror>` を入れても、どの画面でも実行されない |
| S3 | レート制限 | 新規登録・復旧・連携コードの連打が上限で止まる（`auth.py` の各上限） |
| S4 | Cookie | `HttpOnly`・`Secure` が付き、`SameSite` が決めた値になっている |
| S5 | ヘッダ | CSP・`X-Content-Type-Options: nosniff`・`Referrer-Policy: no-referrer` が出ている |
| S6 | ログ | 運用ログ・ホストのアクセスログに、復旧コード・Cookie・感想・利用者 ID が出ない |
| S7 | 秘密情報 | リポジトリと公開されるファイルに API キー・pepper・AWS の鍵が無い（secret scanning を通す） |
| S8 | 依存 | `boto3` などの追加依存の脆弱性を確認する |

### 3-5. 機能（主な流れを手で通す）

| # | 項目 | 合格の基準 |
|---|---|---|
| F1 | はじめて開く | 復旧コードが1度だけ表示され、控える案内が出る。空の状態から「はじめる」に案内される |
| F2 | おすすめ → 興味あり | 押した公演が「興味あり」とカレンダーに出る |
| F3 | 記録 → 評価 → 感想 | 手で足した記録に ◎○△× と感想を付けられ、日記帳に出る |
| F4 | 評価が推薦に効く | 評価を付けたあとにおすすめを開き直すと、反映される（`on_next_read`） |
| F5 | お気に入り | 登録した名前の公演が、次のカタログ更新のあとに「お気に入り」に出る |
| F6 | 別の端末 | 連携コードで2台目から同じ記録が見える |
| F7 | 書き出し | 設定の「書き出す」で、自分の記録だけが JSON で取れる |
| F8 | スマホ | 主要な画面がスマホの幅で崩れず、操作ツアーが最後まで進む |

### 3-6. 性能と運用

| # | 項目 | 合格の基準（数値は決めて書き込む） |
|---|---|---|
| P1 | 応答時間 | おすすめの画面が ___ 秒以内（記録が100件の利用者で） |
| P2 | 同時利用 | ___ 人が同時に評価を付けても、エラーと保存漏れが出ない |
| P3 | 監視 | サーバを止めると ___ 分以内に通知が届く |
| P4 | カタログ作成の失敗 | EC2 の更新が失敗したら通知が届く |
| P5 | 外部への取得 | 1回の更新でホストごとの要求数がログに出て、間隔（1.1秒）が守られている |

### 3-7. 法務・文書

| # | 項目 | 合格の基準 |
|---|---|---|
| L1 | プライバシーポリシー | 公開され、画面から1回の操作で開ける |
| L2 | 利用規約 | 本番向けに改訂し、セキュリティ規約と食い違いが無い |
| L3 | 取得元 | CoRich・ステイジーズ（とくにポスター画像）の利用について、確認した結果が記録に残っている |
| L4 | Gemini | 利用する枠と、送るデータの範囲が記録に残っている |
| L5 | 問い合わせ | 削除依頼・取得の停止依頼の窓口が動いている |

## 4. 持ち主が決めること

コードでは決められないので、先に決めてもらう必要がある。

1. **どこで出すか。** Render を続けるか、Cloudflare に移るか（費用、SQLite と D1 の違い）
2. **どのくらいの規模を想定するか。** 利用者数の目安。これで保存方式、プラン、法務の重さが変わる
3. **無料で出すか。** 有料にするなら決済・特定商取引法の表記が加わる
4. **ポスター画像を出すか。** 許諾が取れない場合の代わり（公式ページへのリンクだけにする等）
5. **見本データの扱い。** 本番では完全に無くすか、チュートリアル専用に残すか
6. **独自ドメイン。** サービス名・ドメインを取るか（Cookie の設定と HSTS に関わる）
