# 本人の評価から次の推薦への接続：実装と検証

記録日：2026-10-12（日本時間）。公開用リポジトリのmaster
`e9eeb8066ba982fcbc224f6b68810c91ff5a1ad3`を基準に実装。

## 今回つないだ流れ

1. 利用者本人の◎○△×／保留を既存のSQLiteへ保存する。
2. 次におすすめを開くと、本人の評価・除外・公演照合・手入力の作り手を読む。
3. 保存済みの全候補のクレジットと照合し、本人の人物得点と理由を計算する。
4. 本人のお気に入り・興味あり・購入済み・除外語を当て、未開幕の推薦を選ぶ。
5. 地域で絞り込み、上位15件を表示する。評価の変更・保留・記録の取り消し、
   復元、公演照合の変更は、この次回計算で反映する。

入力直後にバックグラウンドで推薦を完成させる方式ではない。
評価APIは保存成功と`recommendation.status=on_next_read`を返す。
画面にも「次におすすめを開くと反映」と表示する。感想は従来どおり別に保存する。

## 計算の範囲

`tools/review/user_recommender.py`の`person-feedback-v1`で人物得点を計算する。
人物・役職ごとに、本人の◎率と全体の◎率との差を平滑化・縮約して使う。
役職の既定重みは比較基準として現行値を使い、本人の設定倍率を計算前に適用する。
これらの係数が公開利用者に最適だと検証したわけではない。

- 個人のクレジット実績に◎がない場合、平滑化の事前値だけでは加点しない。
- 得点は正の寄与の上位3件の和。順位の第一軸は出演／履歴2作品以上の一致。
- 完全な寄与一覧を保持し、理由表示用の上位6件を再計算の材料にしない。
- この人物単独モデルでは候補集合のp90で割らない。倍率を掛けても正規化で
  相殺される問題を避けるため、得点は固定尺度のまま使う。
- 同じ公演IDの複数記録は独立作品として重複計上しない。
  代表評価は保存更新日時、観劇日、記録鍵による決定的な順序で選ぶ。
  公演IDが異なる再演の同一作品認定は未実装。題名だけで同一と断定しない。
- 得点ゼロの公演は「好みに合う推薦」と呼ばず、別の`unscored`集合に保つ。
- 候補が同一ツアーなら1枠にまとめ、会場情報を残す。団体・クレジットが異なる
  同題名公演は、この集約では別に扱う。
- 人物の情報がない記録も全体の評価率には含むが、人物の照合には使えない。
  すべて◎の場合も、現行の差分方式では正の寄与が出ない場合がある。

共通`recommend2.json`は候補の補完としてのみ読む。持ち主の得点・人物理由・
題材得点を本人向けの結果へ引き継がず、共通JSONを書き換えない。
候補は`candidates / favourites / calendar / picked`の保存済み全件から集める。
外部取得・LLMは呼ばない。感想引用も本人のものを使う。

## 更新の整合性とデータの由来

推薦画面のAPIではHTML断片キャッシュを使わず、毎回本人の保存状態を読む。
これにより保存前の並行処理が古い推薦を再びキャッシュへ入れる問題を避ける。
プロフィール構築時は同じSQLite読み取りトランザクションで評価・除外・
束ね直し・手入力の作り手を読む。推薦ジョブとプロフィールキャッシュは導入しない。

評価と感想に別々の由来列`verdict_source / note_source`を追加した。
新規見本は`demo`、本人が明示的に書いた欄は`user`、既存の由来不明値は
`legacy_unknown`。感想だけの編集で架空の評価を本人の評価へ変えない。
記録鍵が変わる引き継ぎ処理でも由来を維持する。

**`user`は本人による入力という意味で、本当に観劇したと検証済みという意味ではない。**
デモ上の入力を自動的に品質検証用の実データとは扱わない。実利用／デモ環境、
同意、観劇・入力日時を確認する評価用のデータ抽出は、次の段階で実装する。
由来不明の既存値を、JSONに似ているという理由だけで自動分類しない。

## 検証

一時DB・人工候補を使うHTTP検査で、変更前後の得点・理由・束の移動を検証した。
実データの精度検査ではない。

| 検査 | 結果 |
| --- | --- |
| `python tools/taguri/test_user_recommendation.py` | 34実行通過。既存HTTP検査10件の二重実行を含み、独立した検査は24件 |
| 評価変更・保留・取り消し・復元 | 次回の推薦と理由から古い信号が除かれる |
| 公演照合・解除 | 人物情報の取得／解除が次の推薦に反映する |
| 利用者分離 | 他人の記録を評価できず、本人の編集で他人の推薦を変えない |
| 共通結果・全候補 | 共通JSONを変更せず、共通上位にない候補も本人の実績で推薦する |
| 関連する条件 | 興味ありは追跡枠、明示お気に入りは別枠、地域絞り込みとツアー会場を維持 |
| 平滑化・欠損・重複 | 全低評価・履歴ゼロの架空加点を防ぎ、同じ公演15回を15作品として数えない |
| 保存・由来 | DBを開き直しても保存値が残り、評価／感想の由来を独立に維持する |
| `python tools/taguri/test_seed_demo.py` | 21件通過 |
| `python tools/taguri/test_rebucket.py` | 8件通過 |
| `python tools/taguri/test_auth.py` | 24件通過 |
| `python tools/taguri/test_digest.py` | 31件通過、1件失敗。変更前からある日付見出しの検査不一致。本体はdetails／summary、検査はh3を期待している。GitHubから取得した基準masterの本体・検査にも同じ不一致がある |

`test_rate_performances.py`は実購入データを要求するため、この作業環境では
「作品が足りない」として検査不能。精度合格の根拠にはしていない。

## 残る制約と次の段階

今回の完了条件は「本人の評価が本人の次の推薦へ届く」。**推薦精度の改善は未検証**。
感想の観点分析、意味類似、重みの自動学習、MMR、学習曲線、実利用比較は未導入。

見本96件の公演IDは空のままなので、人物得点に使うには正しい公演との照合か
手入力のクレジットが必要。誤った公演や創作した作り手を自動補完しない。
画面で情報がある評価作品数と、足りない情報の登録先を案内する。

後続段階で、**候補カタログと利用者DB・認証pepperの保存先を分離するコードを実装した**。
`TAGURI_STATE_DIR`で利用者の保存領域を指定でき、`serve_cloud._fetch_catalog()`は
カタログ交換時にも既存のDBを保持する。詳細は[永続保存と運用ログ](demo-state-storage.md)を参照。
ただし、**公開先の永続ディスクは未設定・未検証であり、公開デモの再起動・再デプロイを
またぐ永続保存はまだ確認できていない**。継続的な実利用検証の前に、ホスト側の永続
ディスク設定、同じ認証鍵を含めた移行・バックアップ、再起動・再デプロイ後の復旧確認が必要。
保存先の環境変数を設定しただけでは、ホスト側の永続性を保証しない。

候補数・履歴量による応答時間、同時利用の負荷測定は未実施。
感想・候補・モデルの大きなキャッシュは、版と利用者分離を検証してから追加する。
既存の反応を作品単位で伝播する処理には短い題名鍵を使う箇所が残る。
再演・別団体の同題名作品を正しく分ける安定した作品IDの設計は、別途必要である。
