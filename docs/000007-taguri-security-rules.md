## 1. 「セキュリティを守る」の定義（2026-08-28 改定）

**このシステムはこれまで「公開のサーバもアカウントも持たない、本人が自分のパソコンだけで使う道具」だった。#000008 の決定により、この前提を撤回する。** 撤回の理由: 起案者の希望により、アカウント登録なしで不特定多数がそれぞれ個人的に使えるサービスへ転換したため（[#000008 決定事項1](../tasks/active/current/000008-taguri-public-service.md)）。**新しい前提は「公開された常時稼働サーバを持つが、アカウント（メールアドレス・パスワード）は持たない」である。** 利用者の識別は、復旧フレーズ（マスター鍵）と Cookie（日常鍵）の二層構造のみで行う。

この転換により、「守る」の中身も変わる。もはや「本人 1 人だけが触れる」ことを前提にできないので、次の 4 点を指す。

1. **利用者間の境界を越えさせない（新規）** ── ある利用者の観劇記録・お気に入り・評価が、別の利用者から読み書きできないこと。**アカウントを持たない設計である以上、この境界を保つ唯一の手段は Cookie に載る日常鍵の秘匿性であり、これが破られた場合の被害範囲がそのまま「他人になりすませる範囲」になる。** 今回の転換で最も重い制約である
2. **境界を越えさせない（対外部）** ── 個々の利用者データが、この基盤の外（無関係な第三者・分析ツール・公開リポジトリ）に出ていかないこと。原則は変わらないが、「基盤の外」は「本人のパソコンの外」から「サーバの外」に置き換わる
3. **書き込める操作を数え上げられる状態にする** ── 変更なし。任意の操作を許さず、押せる操作を最初から決められた種類だけに絞る
4. **持ちすぎない（改定）** ── 「常駐させない」は常時稼働が前提になったことで成り立たなくなった。代わりに、**利用者ごとのデータを必要以上に集めない・ログに残さない・第三者に渡さない**ことを指す

**この定義の外にあるもの。** 公演のあらすじ・出演者・劇場座標のような、CoRich などの公開ページから取ってくる情報は、そもそも非公開の情報ではない。この規約が守るのは、**利用者本人がこのシステムに入れた内容と、本人の行動そのもの**（誰を好きか・何を観たか・いつ買ったか）である。

**新しく生じた課題。** 「本人しか触らない」という前提が無くなったことで、これまで規約面（人の運用）に頼っていた約束の一部を、コード面・環境面で技術的に強制する必要が出てきた。3〜5 章の変更点はほとんどがこれに当たる。

## 2. 守り方は 3 層に分かれる

同じ約束でも、**環境・コード・規約のどの層で守っているか**によって強さが違う。環境とコードは技術的に強制されるが、規約は「そう決めた」という取り決めであり、破っても技術的には止まらない。**規約止まりの約束は、実装が追いつくまでの間、破られていないか都度確認する必要がある**（7 章の見つかった食い違いがその例だった）。

| 層 | 何で守るか | 破られたら気づけるか |
|---|---|---|
| **環境面** | OS・ファイルシステム・ネットワークの設定 | 気づきにくい（設定を見に行かないと分からない） |
| **コード面** | プログラム自身が拒否する・検査する | 気づきやすい（動かなくなる／ログに残る） |
| **規約面** | 書いた約束・運用上の習慣 | **人が確認しない限り気づけない** |

| E5 | **サービスは非 root の専用ユーザーで、必要最小の権限に絞って動かす**（旧: 常駐サービスとして OS に登録しない） | systemd 等でサービス化し、実行ユーザー・読み書き可能なディレクトリを限定する。**常時稼働そのものが前提になったため、「持たない」という約束は成り立たない。「絞る」に置き換える** |

| E7 | **復旧フレーズ・連携コードをアクセスログ・エラーログに残さない（新規）** | サーバのログ出力から、リクエストボディと Cookie 値をマスクする |

## 4. 外へ情報を出す場面（改定）

**このシステムは決まった相手にだけ、外部へ接続する。** それ以外への通信（分析・計測・広告のような、本人に見えない裏の通信）は無い。**どの相手にも、その場面で必要な最小限しか送らない**という原則は変わらないが、O2 と O4・O7 の扱いが変わった。

| # | 送る相手 | どんな場面で送るか | 何を送るか | 変更点 |
|---|---|---|---|---|
| O1 | CoRich（`stage.corich.jp`） | サーバ側で 1 本、定期実行（`--fetch` 相当・月 1 回） | 検索条件・公演 ID。個人を特定する情報は乗らない | 変更なし。**全利用者共通の公演情報として、1 本の取得結果を全員で共有する**位置づけを明記した |
| O2 | CoRich（同上・お気に入り名検索） | 1 日 1 回 | **全利用者分の登録名を重複排除した名前の集合** | **旧: 利用者本人の登録名をそのまま検索語として送信 → 新: 名前ごとに 1 日 1 回だけ送信。** 誰が登録したかという個人の識別情報が検索語に乗らなくなった分、旧方式よりプライバシー上も良い。利用者数が増えても送信量は名前の種類数にしか比例しない |
| O3 | CoRich（`stage-image.corich.jp`） | ポスター画像を取り込む | 画像の URL（公演 ID を含む） | 変更なし |
| O4 | Google（`gmail.googleapis.com`） | **公開 v1 では接続しない（凍結）** | ─ | [#000008 決定事項2](../tasks/active/current/000008-taguri-public-service.md) により凍結。理由: `gmail.readonly` は Google 公式の「制限付きスコープ」に分類され、通常の OAuth 審査に加えて年次の第三者セキュリティ評価（費用は無料〜数千ドル規模、毎年更新）が要ることが Google Cloud Console での実機確認により判明したため。個人ポートフォリオ規模には継続コストとして重いと判断した |
| O5 | Google スプレッドシート（`docs.google.com`） | ステイジーズカレンダーを取り込む（毎回） | 何も送らない ── 公開された表を読むだけ | 変更なし |
| O6 | LLM API（あらすじの要素・感情の抽出、年表・相関図の読み文章の作成） | 演目単位で 1 回計算し、使い回す | 公演のあらすじ本文（公開情報）、または集計した観劇の事実 | **月間の支払い上限を追加。** プロバイダ側の予算アラートに加え、アプリ側で一定回数・一定金額を超えたら呼び出しを止めるカウンタを持つ。**用語の補足**: [利用規約第 7 条](000007-taguri-terms-of-use.md)は現在「Claude API」と記載しているが、2026-08-27 の実装変更で実際の呼び出し先は Gemini API に切り替わっている（`tools/llm_gemini.py`）。利用規約側の記載更新が別途必要（[#000008 残課題](../tasks/active/current/000008-taguri-public-service.md)に追加） |
| O7 | 本サーバ（ブラウザ ↔ サーバ間・新規） | 初回登録・端末追加・復旧の各操作 | 復旧フレーズ・連携コード | **新規追加。** E1 の HTTPS が前提。フレーズ・コードは URL クエリに乗せず、POST ボディでのみ送る。サーバ側は生データを一切ログに残さない（E7）。保存するのはソルト付きハッシュのみ（C13） |

**O1・O3・O5 と O2・O6 の違い。** O1・O3・O5 は利用者に依らない共通データの取得で、利用者数が増えても負荷が変わらない。O2・O6 は個人の入力（登録名・観劇記録）に由来するが、**全利用者分をまとめて処理する形にすることで、利用者数の増加が外部送信の増加に直結しないようにしている。**

## 7. 未解決の課題 ── コード・ドキュメントに残る実例

**この規約を書く過程で見つけた課題を、公開前提が加わった今あらためて重く扱う。** データの保存先（`data/review/`・`data/tickets/`）は隔離されているが、**コードの docstring・コメント・関連ドキュメント（`tools/taguri/*.py`・`tools/review/*.py`・`docs/*.md`）には、実測の説明として本人が観た公演の実名・出演者名・登録したお気に入りの名前が多数、具体例としてそのまま書かれている。** これらのファイルは `.gitignore` の対象外で、Git 履歴に残っている。

- **なぜこうなったか。** 実測に基づいて判断を書く、という開発上の規約（具体的な数値・実例を示す）を優先した結果、個人の観劇履歴が実例として大量に組み込まれた。
- **深刻度が変わった。** 元は「社内 GitLab（`internship` 名前空間）だから公開範囲は限定的」という前提で保留されていたが、**個人のポートフォリオとして公開する前提が加わった今、この実例は文字通り不特定多数の目に触れる。公開前に必ず対応する必要がある**（[#000008 残課題](../tasks/active/current/000008-taguri-public-service.md)）。
- **対応は起案者の判断を要する。** 実例を一般化して書き直すか、該当ファイルを非公開のまま別リポジトリに退避するかは、量が大きく（複数ファイルにまたがる）、後から個別に相談して決める。
