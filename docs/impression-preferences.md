# 感想から推薦対象の特徴への好みを更新する

## 動作

作品ごとの感想（`works.note_impression`）で明示された特徴への評価を、次の推薦に反映する。
例：「家族の描写がよかった。でも恋愛は苦手だった。」なら、「家族」に正、「恋愛」に負の
票を入れる。作品全体の ◎○△× とは独立に扱い、× の作品でよかった部分も利用する。

`tools/review/impression_preferences.py` は Python 標準ライブラリだけで動作する。
この処理にAPI料金はかからず、感想の外部送信も行わない。

## 特徴と評価の結び付け

- 特徴は、観た作品の `themes.jsonl` の `rated` 要素、または結び付けた公演の
  `candidate` 要素に限定する。手入力の特徴も、既存の `net_c.load_themes()` 経由で読む。
- 句読点・改行・逆接で節を分け、その特徴に続く近い評価表現を結び付ける。
  別の対象への評価が間に入る文（「家族の話で演技がよかった」等）は保留する。
- 「面白くなかった」「好きではない」は負、「悪くなかった」は弱い正。
  推量や二重否定、同じ特徴への好評と不評が混在する文は保留する。
- 「悲しかった」「苦しかった」だけでは不満と判定しない。
  「最高だった」だけの作品全体の感想を、全特徴への好みとして扱わない。
- 全角・空白の違いと限定した同義語を正規化する。
  例えば「喜劇／コメディ」「会話劇／会話の掛け合い」。
  「恋愛」と「恋愛が多い」は異なる特徴として保つ。

特徴の辞書は既存の公演要素が基準となる。テンポや結末の特徴を推薦に使いたい場合は、
観た作品と推薦候補の両方に、同じ意味の要素を登録する必要がある。
感想だけから公演カタログを書き換えることはしない。

## 好みと順位

同じ作品で何度書いても、1 特徴につき 1 票にする。観劇回数でも票を増やさない。
特徴 e の好みは `評価の合計 / (評価した作品数 + 3)`。
件数が少ないときは 0 に寄せ、複数の作品で繰り返される傾向を強める。

候補公演の特徴に対応する好みを読み、絶対値が大きい上位 3 特徴を利用する。
補正値は `0.75 × 好みの合計 / 3`。特徴の数が多いだけで加点されないよう、分母は固定する。
既存の「題材」の効かせ方の倍率も掛ける。「効かせない」では補正と感想の理由を無効にする。

並び順は `効く人物一致の数 + 補正値`、次に従来の正規化スコア。
弱い証拠で基本順位を大きく変えないための初期設定であり、精度向上を実測した重みではない。
負の補正は順位を下げるだけで、既存の推薦候補を削除しない。
一致する特徴の情報がない候補の補正は 0 とする。

## 利用者ごとの適用

週次の `recommend2.json` は共通カタログの補完に使う。
`app._load(user_id)` は本人の現在の評価を `user_recommender.py` の
`person-ordinal-v3`（2026-10-13 までは person-feedback-v1） に渡して人物得点と理由を計算し、現在の題材情報を当てる。
その後、本人の反応で束を割り振り、現在の観劇記録から感想のプロフィールを作って
推薦枠と未得点の候補を補正する。未得点候補も正の特徴一致があれば推薦に加えられる。
共通一覧を持ち主の順位として利用者に流用しない。

サービス版（Cloudflare Worker）でも同じ補正をかける（#104、`cloudflare/src/impression.js`、
`screens/recommend.js` の `rankedGroups`）。規則は上の移植で、`cloudflare/test/impression.test.js` が
同じ感想に Python と同じ好みと補正を返すことを確かめる。Worker 版の違いは次のとおり。

- 特徴は、観た公演に付いた種類の言葉のうち `#形式`・`#原作`・`#翻訳`・`#原作の国`・`#題材`・`#ジャンル` に限る
  （「使わない」にした種類の理由は除く）。候補の言葉は、好みのある特徴の表記だけを、その特徴が付いていた軸で
  索引（rec_credit）から引く。候補全部の言葉を読み直さない
- 補正には「作品の内容」の効かせ方を掛ける（0 なら補正しない）
- 点の無い公演を感想だけの理由で加えるのは、補正の大きい順に 40 件まで（`IMP_EXTRA`）
- 理由は「感想」の行に、特徴・作品名・感想の一文（40 字まで）を 2 つまで出す
- 外部の LLM は呼ばない（`test/no-llm.test.js`）

CPU（`node cloudflare/scripts/measure_worker_replay.mjs --index … --notes 1`、2026-10-18、手元、中央値の 3 回）:
全部の記録に感想を書いた最悪の場合で、評価 20 件 +5 ms、100 件 +9 ms、300 件 +20 ms。
3 割に感想があると 100 件で +6 ms。控え（rec_cache）が当たる表示では増えない。

感想・引用・好みを共有の推薦ファイルへ書き戻さない。
興味なし、興味あり、購入済み、お気に入り、除外の束はこの補正で動かさない。
未来の記録、「行かなかった」記録、取り消した記録は学習に含めない。
回ごとのメモ（`visit_note`）や観る前の理由（`note_motive`）も読み込まない。

感想の保存・編集・削除で、既存のHTTPハンドラが本人の画面キャッシュを無効化する。
次に画面を取得すると、好みと引用の両方を現在の記録から作り直す。
推薦理由には特徴、根拠の作品数、元の感想の一節を表示する。内部の数値は表示しない。

## 検証と制限

```bash
python3 tools/taguri/test_impression_preferences.py
python3 tools/taguri/test_rebucket.py
python3 tools/taguri/test_demo_stability.py
```

一時DBと架空の公演で、否定・複数の特徴・曖昧な文・重複票・利用者間の分離・
感想の保存／編集／削除・題材の無効化・候補生成から画面への接続・引用のHTMLエスケープを検査する。
テストでは外部通信を禁止する。

上記は新規 31 件、既存の振り分け 8 件・デモHTTP 10 件を検査する。
既存の `tools/review/test_rate_performances.py` は実データを前提とするため、
公開リポジトリだけの環境では必要な観劇記録がなく実行を完了できない。

ルールは限定的で、皮肉や複雑な係り受け、辞書にない言い換えは読み取れない。
感想に特徴が明示されていない場合も補正しない。抽出精度と推薦品質の向上は、
実際の感想の人手判定と、その後に観た公演の評価で別途測定する必要がある。
