# たぐりの推薦を良くする機能案とUI/UX検討

- 記録日：2026-10-11
- 状態：検討案。以下の機能・画面変更は未実装で、効果も未検証。
- 目的：自分に合う演劇を、上演前に見つけて選べるようにする。
- 前提：**推薦がメイン。記録、感想、好みの設定、比較は、次の推薦と選択を支える。**
- 参照：[README](../README.md)、[既存の設計書](000007-taguri-design.md)、
  [今回実装した感想による順位補正](impression-preferences.md)。

現状の把握は公開コードと設計資料に基づく。実際の利用者の操作観察や、
スマートフォンでの画面評価を実施した結果ではない。
感想による順位補正もローカルの変更であり、公開デモへ反映済みとは扱わない。

画面構成・初期実装の詳細は[推薦UI/UX詳細設計](recommendation-ux-design.md)で決定。
根拠と閲覧範囲は[文献調査](research/recommendation-ux-literature.md)に記録した。
本書の機能案を一度に実装する方針ではなく、詳細設計の段階に沿って検証する。

## 1. 何を良くするか

たぐりの中心の体験は「おすすめを見る → 気になる公演を選ぶ → 観る → 次の推薦が育つ」。
機能を増やす判断は、推薦が好みに合うか、新しい公演に出会えるか、観に行く一本を
選びやすくなるかで行う。記録件数や設定の操作回数が増えただけでは成功としない。

特に、次の三つを分けて評価する。

| 目的 | 確かめたいこと | 注意点 |
|---|---|---|
| 好みとの一致 | 推薦から選んで観た公演が本人に合ったか | 観なかった候補の満足度は不明。興味ありだけでは当たりを判断できない |
| 発見 | 知らなかった劇団・表現の公演で、観たいものが見つかるか | 新しい名前が出るだけでは価値にならない |
| 選択のしやすさ | 自分が行ける候補を、少ない負担で選べるか | 閲覧時間が短いだけでは、選べたのか離脱したのか分からない |

## 2. 機能案と優先順位

### 第一候補：推測した好みを確認・修正できる

感想から読み取った特徴への好みを、根拠と一緒に示す。
「恋愛が苦手」と「この作品の恋愛の描き方が苦手」を区別できるようにする。

例：推薦理由の詳細に次の確認を置く。

> 《観た作品》の感想「恋愛描写は苦手だった」から、恋愛を扱う公演の順位を少し下げています。
>
> ［好みとして合っている］［この作品だけ］［読み取りが違う］

| 回答 | 推薦への反映案 |
|---|---|
| 好みとして合っている | この感想の解釈を確認済みとして残す。1回の確認だけで強い好みに固定しない |
| この作品だけ | この感想を他作品への一般的な好みの学習から外す。元の感想と作品評価は残す |
| 読み取りが違う | この解釈を取り消す。必要なら好評・不評・判断しないを任意で選び直せる |

確認は推薦を見る前の必須作業にしない。未回答なら弱い補正に留める。
解除・再修正を可能にし、原文を編集したら古い確認をそのまま再利用しない。
特徴名と意味も重要で、「恋愛」と「恋愛要素が多い」を一括りにしない。

### 第二候補：推薦が合ったかを観劇後に振り返る

既存の◎○△×による「自分に合ったか」の評価を中心に使う。
追加するなら「期待どおり／予想外によかった／合わなかった」などを任意で添える。
満足度と期待との差は別なので、この追加回答だけを正解ラベルにしない。

推薦時に示した理由と観劇後の反応を結び付け、「会話劇だから推薦したが、
よかった理由は身体表現だった」のようなずれを確認する。
回答は評価を付ける同じ場面に置き、別の振り返り画面へ必ず移動させない。

### 第三候補：いつもの好みと、今の気分を分ける

推薦画面で「今日は笑えるもの」「余韻を楽しみたい」などを任意で指定する。
長期的な好みのプロフィールへ自動で書き込まず、期間を明示した一時条件として扱う。
解除と「いつものおすすめに戻す」を分かりやすくする。
気分に合う公演を判断する情報が足りないときは、合っているように装わない。

### 第四候補：少し好みから離れた公演を混ぜる

既知の好みに合う候補を基本に、知らない劇団・表現の候補も少量提示する。
「いつも好きな題材ですが、初めての劇団です」など、試す理由を示す。
探索は推薦本体の中で扱い、別の大量一覧を増やすことを既定にしない。
比率・件数は未決定。既存の上位15件すべてを置き換える前に小さく比較する。

### 第五候補：気になる推薦候補を比較する

推薦から興味ありにした2〜3件を、日程・場所・価格・特徴・推薦理由で比較する。
比較は迷ったときに開く補助機能とし、推薦を見るための前提にしない。
日程・場所などの既知の条件で候補を絞ることと、作品の好みを学習することは分ける。
「行けない」ことを作品への不満として学習しない。
価格や販売状況が不明なら不明と示し、推測した完売や残席を表示しない。

## 3. 推薦を主役にするUI/UX

### 入口と情報の優先順位

推薦を出せる状態では、「今週のおすすめ」を最短で開ける入口にする。
初回で材料が少ないときも、好みの設定をすべて終えることを要求せず、
推薦に必要な最小限の条件・入力で始められるか検討する。

既存の複数の画面は用途を保ちつつ、主な行き先を「おすすめ」「興味あり」「観た公演」
として理解できるか試す。ナビゲーションを直ちに統合する決定ではない。
記録の図や詳細設定を推薦より先に見せる必要はない。
お気に入りに当たる新着のお知らせと、推定で順位を付ける推薦は区別を保つ。

推薦画面で読む順序の案は次のとおり。

1. 行ける地域・期間と、今回のおすすめ。
2. 公演カードと「興味あり」の操作。
3. 推薦理由の詳細、好みの修正、任意の気分指定。
4. 観劇後の評価待ちや詳しい設定への入口。

設定や未評価件数が、公演一覧の初画面を占有しないか確認する。
15件という現状の上限は維持を出発点にし、必要なら段階表示との比較を行う。

### 推薦カード

最初に題名、場所・日程、推薦理由の要点、「興味あり」を見せる。
長いあらすじ、複数の人物履歴、感想の全文は、求めたときに開ける形を検討する。
ポスターだけで公演を識別させない。

理由の要点は「会話劇を楽しんだ感想と共通する特徴があります」のように、
選ぶ助けになる一文にする。詳細では元の作品・感想と、訂正する入口を示す。
「あなたは恋愛が嫌いです」のように断定しない。
システム内部のスコアや信頼度の数式は、選択のための必須情報として置かない。

### 入力と反映

好みの確認、観劇後の振り返り、感想はすべて任意にする。
推薦理由の修正を何度も求めたり、保存するたびに確認モーダルを開いたりしない。
感想を自然に書けることを優先し、解析に合わせた定型文を強制しない。

修正した結果は「次におすすめを開くと反映します」と伝える。
現在の実装は次の画面取得で反映するため、即時にカードが並べ替わるような説明はしない。
将来その場で反映する場合も、読んでいるカードが突然移動しない更新方法を検証する。

### 迷い・待ち時間・情報不足

読み込み中は、読み込み中であることを示す。記録なし・条件に一致する公演なし・
情報不足・通信失敗を同じ空画面にしない。
候補がないときは、条件を緩めるなどの次の行動を示す。
推薦理由が弱い候補を強く言い切らず、根拠のある推薦と試す候補を理解できるようにする。

スマートフォンでの読みやすさを重視する。主操作を小さなアイコンだけにせず、
評価を色だけで区別しない。キーボード操作、フォーカス、読み上げ時の操作名も確認する。
比較は狭い画面で横に大きな表を置くより、項目ごとに候補を並べる案も試す。

## 4. 検証すべき仮説

| ID | 仮説 | 方法・見る指標 | 採用の判断／見直す条件 |
|---|---|---|---|
| V1 | 感想から特徴と評価を正しく結び付けられる | 実際の感想を人手で判定し、特徴・評価・対象の組の適合率、抽出できた割合、誤りの内訳を測る | 明示的な不評、悲しさの表現、作品固有の不満で重大な誤りが多ければルールと適用範囲を狭める |
| V2 | 好みの確認は、誤った一般化を修正できる | 「この作品だけ」等を説明できるか観察。修正前後の推薦、取り消し率、操作時間を確認 | 意図どおり訂正でき、推薦の選択を邪魔しない場合に採用。確認の完了率だけでは判断しない |
| V3 | 感想の補正で推薦の質が上がる | 同じ候補・同じ条件で補正なし／ありを比較し、その後の観劇評価と選択を追う | 好みへの一致が改善し、候補の多様性・選択負担が悪化しないこと。テスト通過を精度向上の証拠にしない |
| V4 | 観劇後の追加質問は、推薦理由の改善に役立つ | 既存評価のみと任意の追加回答を比較。回答から原因を区別できるか、評価の完了率を確認 | 新しい情報が得られ、既存の評価を残す負担が増えすぎない場合に採用 |
| V5 | 今の気分を指定すると今回の選択が楽になる | 気分指定の有無で選べた割合、条件の理解、解除できた割合を比較 | 今回の候補が選びやすくなり、長期の好みが変わるという誤解がなければ採用 |
| V6 | 探索候補は価値のある発見を増やす | 未知の公演への興味あり、観劇後の評価、提示の多様性を比較 | 新規性だけでなく、観たい・観てよかった公演が増えること。満足度が落ちれば比率や理由を見直す |
| V7 | 候補比較は迷いを減らす | 2〜3件から選ぶ課題で、選択完了率・時間・選びやすさを確認 | 選べるようになり、推薦から比較への追加操作の負担を上回る効果がある場合に採用 |
| V8 | 推薦中心の入口と短いカードで選びやすくなる | 現状と試作で、最初に推薦へ到達できるか、理由を理解できるか、公演を選べるかを比較 | 所要時間だけでなく完了率と理解が改善すること。必要な情報が隠れて判断できなければ見直す |
| V9 | 修正・削除の反映を利用者が理解できる | 感想編集→推薦を再表示する課題で、保存状態と変化を説明できるか確認 | 古い好み・引用が残らず、いつ反映するか分かること |
| V10 | 推薦を妨げない操作・表示になっている | スマートフォン、キーボード、読み上げで推薦閲覧・興味あり・理由確認を実施 | 主操作を完了できること。必須設定、読めない比較、操作後の焦点喪失があれば先に直す |

## 5. 検証の進め方

### 最初に確かめる

実際の感想でV1を測り、どの特徴を公演カタログと共有できるかを確認する。
文章の全体的な好評・不評だけでなく、「何についての評価か」が合っている必要がある。
語の一致がなくて読み取れない例も数え、抽出できた例だけで成功率を出さない。

次に、推薦カードの要点・詳細・好み修正の小さな試作でV2とV8を検証する。
まず少人数で操作を観察して問題を見つける。少人数の結果で統計的な効果を断定しない。

### 推薦品質を測る

過去の記録で測る場合は、時点を分け、その時点までの感想で以降の公演を予測する。
評価対象の公演の感想を、その公演を推薦するための学習に使わない。
初期段階では同じ人の補正なし／ありの順位を比較し、次に実際の推薦と観劇を追う。

候補、提示順位、使った推薦理由、推薦方式の版、日時と反応を利用者ごとに記録する。
日程・場所・予算で見送ったものは好みの負例にしない。
表示されなかった・観なかった公演も不評とは扱わない。
提示された順位の差がクリックや選択に与える影響を考慮する。

効果を確かめる実験は、指標・期間・採用する最小の改善幅を事前に決める。
必要な人数・期間は現状の利用数と観劇頻度を見て決め、根拠のない目標値を置かない。
感想や好みの引用を共有カタログへ混ぜず、検証用の記録も利用者を分ける。

### UI/UXで使う共通の課題

1. 行ける地域・期間に合うおすすめを開き、一本を「興味あり」にする。
2. なぜその公演を薦められたかを説明し、根拠の感想を見つける。
3. 間違った好みを「この作品だけ」と修正し、反映する時点を確認する。
4. 観た公演の評価を残す。追加の質問には答えずに完了する。
5. 候補がない／読み込みに失敗した状態から、次の行動を選ぶ。

初めて使う人と既に記録がある人、スマートフォンとPCを分けて観察する。
完了率、所要時間、迷った箇所、理由を理解できたか、主観的な選びやすさを記録する。

## 6. 当面の実装順

| 段階 | 対象 | 次に進む条件 |
|---|---|---|
| 1 | 特徴・評価抽出の実データ検証、推薦カードと好み修正の試作 | 誤った一般化と操作上の問題を把握できている |
| 2 | 好みの確認・修正と、推薦理由からの導線 | 訂正が順位・根拠に反映し、推薦を見るための必須操作になっていない |
| 3 | 既存評価を使った推薦品質の測定。必要な場合だけ振り返りを追加 | 補正の効果と限界が分かり、追加質問の価値を確認できる |
| 4 | 気分指定・探索候補・比較を個別に試す | 推薦の一致・発見・選択を改善する仮説を、各機能で検証できる |

プロフィールの大きな専用画面や分析ダッシュボードを先に作るより、
**おすすめを開いて、公演を選び、間違った推薦理由だけを直せる**体験を先に整える。
新機能を一度に追加すると原因を切り分けにくいため、推薦への効果を確かめながら進める。
