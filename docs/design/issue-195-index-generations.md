# 推薦の索引を分けて送る途中の、新旧の混ざりを抑える（issue #195 の設計案）

確認日: 2026-10-18。対象: ブランチ fix-g4（master `0217394` から）。**実装はしていない。** 本番の D1 での故障注入はしていない。

## 結論

**全部の表を 2 世代持つ方式は採らない。** 代わりに次の 2 つを入れる（書き込みはほぼ増えない）。

1. **公演ごとにまとめて送る。** SQL を「表ごと」ではなく「公演ごと」（その公演の `rec_stage`・`rec_credit`・`rec_people`）に並べ、1 MB に分けるときも公演の切れ目でだけ切る。1 つのファイルが D1 の側でまとめて当たる（途中で止まれば戻る）なら、どの公演も「全部古い」か「全部新しい」のどちらかになる
2. **更新中の印を置く。** 最初のファイルの先頭で `rec_meta 'index_state'` を `updating:<版>` にし、最後のファイルの末尾（`index_rev` と同じ所）で `ready:<版>` にする。Worker は `updating` の間、推薦の答えを `rec_cache` に控えない（混ざった中身で作った答えを、その日のあいだ使い回さない）

保証の単位は「1 つの公演」とする。公演をまたぐもの（同じ公演の別の会場＝`tour`、題名の 2 文字の束＝`rec_gram`）は、更新中は新旧が混ざりうることを仕様として書き、Worker は「見つからない公演は飛ばす」で耐える。

## いまの送り方

| 段 | 何が起きるか | 場所 |
|---|---|---|
| 差分を作る | 表の順（`rec_stage`→`rec_credit`→`rec_people`→`rec_gram`）に、表ごとに「消す行」→「upsert する行」を並べる。版はいつも `live` | `cloudflare/scripts/build_recommend_index.py:445`、`:543-561` |
| 予算で切る | 変わる行が多い日は、公演ごとにまとめて開幕の近い順に選ぶ（選ぶのは公演単位） | `build_recommend_index.py:527-541` |
| 末尾 | `index_rev`（途中の日は `版-left残り`）と `current` を書く | `build_recommend_index.py:563-568` |
| 分ける | 1 行 1 文のまま 1 MB ずつ `index-upload-01.sql …` に分ける。切れ目は文の切れ目だけで、表や公演は見ない | `cloudflare/scripts/deliver_catalogue.py:215-235` |
| 送る | ファイルを名前の順に 1 つずつ `wrangler d1 execute --file`。どれかが失敗すると `pipefail` で止まり、`commit` しない（次回は同じ差分を送り直す） | `tools/taguri/deploy/github-actions/catalog.yml:133-148` |
| 読む | Worker は `ver=(SELECT v FROM rec_meta WHERE k='current')` で読み、控えの印に `index_rev` と今日の日付を入れる | `cloudflare/src/screens/recommend.js:288-296`、`:301-302`、`:432` |

選ぶときは公演単位なのに、並べるときに表ごとに並べ直しているので、ファイルの切れ目で公演が割れる。例えば 01 に `rec_stage` が全部、02 に `rec_credit` の前半が入ると、01 と 02 のあいだに読んだ画面は「新しい会期・古い出演者」を見る。02 で止まると、次の実行（多くは翌日）までその状態のまま。`index_rev` は末尾でしか変わらないので、その間に作った推薦の答えは古い `index_rev` の印で控えられ、その日のあいだ使い回される。

カード（`rec_card`）と題名（`stage_label`）は版を分けて入れてから切り替えている（`scripts/build_cards.py:204-211`）ので、それ自身は混ざらない。ただし索引と同じ日の同じ中身から作るとは限らない（索引だけが途中の日がある、`deliver_catalogue.py:355-369`）。

## A の形

- `diff_sql`（`build_recommend_index.py:507`）で、変わる行を `_stage_of` で公演ごとに集め（選ぶときと同じ関数、`:501-504`）、公演ごとに「消す→upsert」を `rec_stage`・`rec_people`・`rec_credit` の順に出す。公演に属さない `rec_gram` は最後にまとめる
- 1 文に複数の公演の行を入れてよい（`_inserts` の 90 KB の上限はそのまま）が、文の区切りに「ここで切ってよい」印（例: `-- cut` の行）を入れ、`split_upload` は印の所でだけ切る。1 つの公演の塊が 1 MB を越えることは無い（最大でも出演者数百行）
- 先頭の `DELETE … WHERE ver<>'live'`（`:516`）は 01 に残す

## B の形

- `diff_sql` の最初の文を `INSERT INTO rec_meta(k,v) VALUES('index_state','updating:<版>') …`、最後を `'ready:<版>'` にする。差分が 0 の日は書かない
- `screens/recommend.js:288` の問い合わせに `index_state` を足し、`updating:` で始まるときは `rec_cache` への書き込み（`:432`）を飛ばす。読み（控えを使う）も飛ばすかは、更新中の読みが増える量（利用者の推薦 1 回ぶん）を見て決める
- 送るのが途中で止まった日は `updating` のまま残る。次の実行がまた最初から送るので、そこで `ready` になる。長く残ったら `/api/health` に出す（`health`、`worker.js:256`）

## 移し方

1. `diff_sql`・`split_upload` を変える。出す SQL の中身（どの行をどう書くか）は同じで並びだけが変わることを、`test_recommend_index.py` に「並べ替えた前後で、全部当てた後の表が同じ」として足す
2. 故障注入の試験（issue の完了条件）: 手元の SQLite に前の版を入れ、分けたファイルを 1 つずつ当て、**各ファイルの後で**「どの公演も `rec_stage`・`rec_people`・`rec_credit` が同じ版のハッシュ」になっているかを見る。ファイルの途中で止めた場合は、そのファイルが当たらなかった状態と同じになるか（D1 の import がファイル単位で戻るか）を、試験用の D1 で 1 回確かめる
3. B の Worker 側は、印が無い（古い送り方の）ときは今までどおり動くようにしてから入れる

## 無料枠

- A: 0。B: 1 日 2 書き込み、読みは増えない（同じ問い合わせの列が 1 つ増えるだけ）
- C を採ると、差分の書き込みが毎日 2 倍。ふだんの日（`rec_stage` 145 行の日、`docs/knowledge/notes/index-only-run-1016.md`）は収まるが、初回・出演者の大きな直しの日は 1 日 8 万行の取得の予算に収まらない

## 分からないこと・危うい点

- **D1 の `execute --file` が 1 ファイルをまとめて当てる（途中で止まれば全部戻る）かは、公式の文書で確かめていない。** wrangler は失敗時に「元に戻る」と出し、7009 のときは D1 の側で最後まで当たっていた（`docs/knowledge/notes/d1-upsert-counts.md`）。ファイル単位で戻らないなら、A の保証は「1 文の中の行」までに下がる。その場合は 1 文 = 1 公演にする（文の数は増えるが書き込みは同じ）
- 公演をまたぐ混ざり（同じ `tour` の別の会場が新旧で違う、`rec_gram` が消えた公演を指す）は残る。Worker が見つからない公演を飛ばすことは、`stage-search.js:60-75` と `recommend.js:525-545` で確かめる必要がある
- 推薦の答えを控えない時間が長いと、その間は読みが増える（1 回の推薦で数千行）。送るのは 1 日 1 回・数分なので小さいと見ているが、測ってはいない
