01自己紹介

自己紹介

研究・興味関心

情報可視化

Storyline 可視化における複数粒度間のレイアウト一貫性向上手法の提案

  • 課題：既存の Storyline 可視化は、線の交差が少なくなるようにレイアウトを計算していた。しかし「都道府県」「市区町村」など空間スケールが異なると、それぞれ独立にレイアウトを計算していたため、同じ対象の縦の並びが粒度間でずれてしまい、比較したいときに同一の対象を探しにくかった。
  • 提案：複数粒度で描いても並びが一貫するような指標を導入した。また「交差数が最小のレイアウト」と「粒度間で並びが揃うレイアウト」のトレードオフを、利用者が用途に応じて自分で調整できるパラメータを設けた。

02企画内容

知識処理システム企画内容

現状

  • 舞台演劇は、公演が終わってしまうと二度と観ることが出来ないことが多い(映像化もされないことが多い)
  • 今後開催される演劇の公演は膨大にある（本稿執筆時点で 1,299 件）
  • 自分にあった公演は自分の経験と勘で探している

課題

自分が好きそうな・興味がある作品を、開幕までに探すことが困難である。

舞台作品を開幕前までに推薦するシステム

効果

  • ①探す手間が減る：好きそうな公演を、自分で探し回らなくてよくなる
  • ②見逃しが減る：開幕が近づくまで知らせ続けるので、うっかり見逃さない
  • ③記録が残る：公式サイトの公演ページが消えても、自分の記録は残る

対象ユーザー

演劇鑑賞する人（特に、年間数十本観る人や、追いかけている対象〈人、団体、題材など〉がある人に効きやすい）。

想定シーン：どんなときに開くか

次に観るものを決めたいとき

推薦を見て、興味あり・お気に入りを選ぶ。

外で 1 件の公演情報を見かけたとき

気になる人・団体が出ると知って開く。

観た公演の記録・評価を残したいとき

感想を書き、◎○△× を付ける。

見逃しに気づいたとき

あとから「観ればよかった」を登録する。

03機能概要

機能概要

機能の分類・使い方から、使っている技術・システム構成・設計判断までをまとめて示す。効果やメリットの文章は置かず、すべて 5 章にまとめている。

3-1　機能の 4 分類と一覧：記録する・見る／学習する／推薦する／評価する

3-2　ユーザーの使い方

推薦を使う場合（週 1 回・約 3 分）

① へ戻る（週 1 回の輪）

記録を残す・見たい場合（買うたび・観たあと）

推薦を使わず記録だけを残す使い方も成立する。

公演を買う何もしない（メールから自動で取り込む）
観る―
ショートカットから起動記録を残す・振り返るときに毎回
記録を残す感想を書く（1〜3 分）
振り返る眺める・観劇史年表・日記帳

3-3　使っている技術・システム構成

保存の 2 種類を、具体的に言うと次のとおり。

  • 状態（ratings.db、SQLite）：自分にしか作れないデータ。失うと戻らない
    • 観た公演の評価・感想（works／ratings）
    • 「興味あり」「観ればよかった」などの反応履歴（reaction）
    • お気に入り・除外にした名前（splits／excluded）
    • 購入確認メールのチケット情報（ticket）
  • 取得物（JSON・JSONL）：外部から取ったデータのコピー。消えても取り直せる
    • 候補一覧（candidates.jsonl）
    • あらすじ（synopsis.jsonl）
    • クレジット（credits.jsonl）
    • ステイジーズカレンダー（calendar.jsonl）

JSON と JSONL は、データの形で使い分けている。同じ形の行がたくさん並ぶもの（候補・あらすじ・クレジット・カレンダーのように、1 行が公演 1 件やクレジット 1 件を表す）は JSONL（1 行 1 件）にし、複数の情報を組み合わせた 1 つのまとまり（推薦の計算結果など、行の集まりではない構造）は JSON にする。JSONL には副次的な利点もある ── 1 行が壊れても、他の行はそのまま読める。1 つの大きな JSON にまとめていた場合、1 か所の書き込み不良がファイル全体を読めなくするが、1 行 1 件にしておけば被害がその 1 行に閉じる。

3-5　設計判断：測って選んだところ

  • 状態は SQLite 1 本に集め、取得物は JSONL のまま置く。画面が書き戻すのは状態だけなので、状態が 2 つの形式に分かれると反映漏れが起きる。
  • LLM は Gemini API を呼ぶ。urllib で REST を直接叩き、専用の SDK は使わない。入出力を JSON に固定しているので、呼び出し方が変わっても中身は変えずに済む。
  • 常駐しない。127.0.0.1 に固定し、起動ごとに変わるトークンを持たない要求は受け付けない。受け付ける操作は列挙した数個だけ。閉じるとプロセスが落ちる。
  • 技術スタックは Python・SQLite・素の HTML/CSS/JS。表示側にフレームワークを使わず、AI への依存は共通の呼び出し口（tools/llm_gemini.py・Gemini API）1 か所に絞っている。

05達成事項

達成事項

実現できたこと（動作を確認した事実）と、それによるユーザーへのメリット（何が良くなったか）を対で示す。実装できなかった範囲は省略しない。

5-1　実現できたこと・ユーザーへのメリット

1

推薦が反応で変わる仕組みを確認した

「興味あり」（見逃して悔しかった「観ればよかった」も同じ扱い）は作り手・出演者の名簿に ◎ より弱い正例として加わり、次の推薦に反映される。本番データで実際に動かし、名簿が 1,305 件 → 2,116 件（うち 999 件が興味あり・観ればよかった由来）に増え、◎ の基準は動かないことを確認した。

メリット：使うほど、自分に合った推薦に近づいていく。

2

公演情報を、公式サイトの掲載が終わる前に取得し保持している

公演前に取得するので、公式サイトの公演ページが上演後に次の公演の情報へ入れ替わっても（実測 7 件中 5 件）、システム内の記録は消えない。

メリット：公式サイトの公演ページが消えても、自分でアーカイブを探さなくて済む。

3

観劇の歴史を年ごとにまとめ、LLM が傾向を分析する（観劇史年表）

本数を数えるだけでなく、通う劇場・作り手・題材がいつ入れ替わったかを LLM が文章で示す。

メリット：自分の観劇の傾向や変化を、自分で数えたり書き出したりしなくても得られる。

4

公演初日までの推薦と、開幕リマインドの二段構えで知らせる

週次の推薦は期待度順に週 15 件出す。

「興味あり／なし」を押すとその作品は候補から外れる → 次点の公演が繰り上がって入れ替わる。

初日までに一度も推薦へ出ない公演は残る可能性を回避するため

開幕リマインド（今週開幕／来週開幕から、好みに関係なく全公演を出す仕組み）

メリット：情報を見逃して公演の開催を知らずに観逃した、という後悔を防げる。

5

履歴から好みを自動で推定し、公演の候補を提示する

候補は本稿執筆時点で 1,299 件あり、自分で確かめなくても対象が絞られている。

メリット：公演を調べるという手間が多少削減できる。

5-2　実装できなかった範囲

写真からの公演特定未着手

残り 3 日の納期で「一周動く」ことを優先し、後段に回した。

名前・題材での検索の高度化、記録を見返す画面の作り替え一部のみ実装

同上。一周が閉じたあとに回す判断。

未回答の推薦枠が翌週も残り、枠が詰まる問題直さないと決定

畳むと本人の意思と関係なく視界から消えるため。限界として明記し、母集団の拡張で対応する方針。

裏方（美術・音響など）の役職を判別に使う使わない決定

実測で判別力ゼロ（AUC 0.500、裏方だけの名簿は当たった作品が 0 件）。表方だけでも同じ 0.661 だった。

あらすじの題材（網 C）でのランキング使わない決定（2 段階で検証済み）

① 語のまま使うと不成立（AUC 0.551±0.167）。② 意味の近い語をグループにまとめ直しても、判別力が上がったのは取り直し 40 回中 19 回で半分にとどまった。どちらもスコアには使わず、理由の表示にだけ残している。

会員登録・サーバーを越えた同期作らない決定

127.0.0.1 固定という守りが崩れるため。持ち出しは記録一式の ZIP ダウンロードまでに限定。

06今後の展望

今後の展望

気になるけど、追うほどではない要素を弱く効かせる仕組み

お気に入り（無条件に必ず出す）と出さない語（無条件に必ず外す）の中間に、点数を少し上乗せするだけの第 3 の枠を作る案。実データでの需要（該当件数）を見てから作るかどうかを決める。

他の領域への応用可能性

演劇に限らず、ライブ音楽・映画・展示会やアート系イベントにも、同じ「網」の考え方を応用できると考えている。あらすじ抽出の仕組みを応用すれば、書籍などテキスト中心の対象にも広げられる。フリーマーケットのようなイベントも、出展者・出品物についてある程度の情報がそろっていれば対象になり得る。

あらすじから想起される感情を推薦に反映する

現在のあらすじ抽出は題材とトーンにとどまっている。悲劇・喜劇のように、そのストーリーが観客に呼び起こしそうな感情までLLMで分析し、推薦の判断材料に加えることを検討している。
